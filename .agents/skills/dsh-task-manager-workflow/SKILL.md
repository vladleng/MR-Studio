# Работа агента с DSH Task Manager

Агент ведёт журнал, пользователь принимает результат. Скилл описывает работу с задачами, а не процесс разработки конкретного проекта. Соблюдай текущий запрос и инструкции проекта; этот скилл не даёт дополнительных полномочий, не задаёт версии, ветвление или правила выпуска.

## 1. Определи режим

- **Вопрос, анализ, диагностика:** только читай и объясняй. Не создавай задачи, не меняй статусы и не начинай реализацию.
- **Явное поручение выполнить работу:** веди назначенную задачу в пределах согласованного объёма.
- **Приёмка или просьба изменить журнал:** выполни только явно подтверждённое действие.
- Вызов скилла сам по себе не является разрешением на реализацию, изменение структуры проекта, merge или публикацию.

## 2. Найди задачу и зафиксируй границы

1. Используй `tasks_list`, при известном проекте — с `projectId`; затем `tasks_get` для выбранной задачи и её родителя, если он есть. Ориентируйся на ID, не только на совпадение названий.
2. Прочитай описание, критерии приёмки, чек-поинты и последние существенные комментарии.
3. Перед работой кратко зафиксируй цель, разрешённый объём, исключения и достаточные проверки. При ясном поручении повторное разрешение на каждый шаг не нужно.
4. Если запись отсутствует, сначала согласуй её формулировку; уже однозначно сформулированное и одобренное поручение можно оформить без повторного вопроса. Не создавай дубликаты.
5. Не перестраивай чужой план, не заводи новые этапы и не меняй задачи за пределами назначенной работы. Не расширяй объём своим планом; если расширение необходимо, остановись и согласуй его.

## 3. Используй статусы последовательно

| Статус | ID инструмента | Когда использовать |
| --- | --- | --- |
| Бэклог | `backlog` | Работа отложена или ещё не согласована к выполнению. |
| Todo | `todo` | Объём определён, задача ожидает начала. |
| В работе | `wip` | Агент начал выполнять согласованный объём. |
| Wait | `wait` | Результат передан пользователю и ожидает приёмки. |
| Блок | `blocked` | Продолжение невозможно без конкретного внешнего условия. |
| Готово | `done` | Пользователь явно принял результат этой задачи. |

- Это ручные состояния, а не обязательная цепочка переходов. Меняй статус по факту, не ради оформления отчёта.
- Неудачный тест, сложность или необходимость дальнейшего исследования сами по себе не означают «Блок», пока агент может продолжать работу.
- При блокировке запиши причину, что уже проверено, точное условие разблокировки и требуемое действие. После устранения условия верни задачу в `todo` или `wip` по фактическому состоянию.
- Обычное ожидание приёмки — `wait`, не `blocked`. Если пользователь вернул результат на доработку, переведи `wait` → `wip` и уточни замечания в рамках задачи.
- **Статус и прогресс независимы.** Wait не считается завершением. Полный прогресс не разрешает автоматически закрывать задачу или её родителя.

## 4. Веди компактный журнал

Разделяй записи по назначению:

- **Описание задачи:** цель, контекст, что входит и не входит в объём, проверяемые критерии приёмки.
- **Подзадачи:** самостоятельные части работы со своей приёмкой; создавай только в согласованной структуре.
- **Чек-поинты:** конкретные проверяемые шаги внутри задачи, а не замена дерева подзадач.
- **Комментарии:** существенные решения, изменение условий, блокировки, результаты проверок и передача работы. Не записывай каждую команду и не дублируй большие логи.

Технический чек-поинт можно отметить `done`, когда его критерий действительно проверен. Чек-поинт «Пользовательская приёмка» — только после подтверждения пользователя. Завершение чек-поинтов не означает приёмку всей задачи.

Для проверок различай **PASS / FAIL / NOT TESTED**. Указывай фактическую проверку, результат и ограничения; не выдавай тесты, сборку или собственное ревью за пользовательскую приёмку. Не придумывай проценты по числу пунктов чек-листа.

## 5. Используй инструменты журнала

- Чтение: `tasks_list`, `tasks_get`.
- Создание и изменение задач: `tasks_create`, `tasks_update`; подзадача задаётся через `parentId`.
- Чек-поинты: `tasks_checkpoint_add`, `tasks_checkpoint_update`, `tasks_checkpoint_delete`.
- Существенные записи: `tasks_comment_add`; исправление ошибочного комментария через удаление — только в разрешённом объёме.
- Удаление задач, комментариев, чек-поинтов и архивирование не являются обычным завершением работы. Не выполняй их без явного основания и разрешения; `done` не означает «удалить» или «архивировать».

Проверяй результат инструмента: считать изменение сохранённым можно только после успешного ответа. Если инструмент недоступен или запись не удалась, сообщи ограничение. Не обходи инструменты прямой записью в JSON-хранилище и не создавай параллельный файловый журнал.

## 6. Передай результат на приёмку

Когда согласованный объём подготовлен:

1. Запиши короткий итог: что сделано, какие критерии проверены, что не проверено, известные ограничения, где результат и что именно требуется проверить пользователю.
2. Для разработки добавь ветку, commit и ссылку на артефакт, только если они действительно существуют и относятся к задаче. Для других работ укажи соответствующий результат; не требуй Git или сборку там, где они не нужны.
3. Поставь `wait` и сообщи «ожидает приёмки». Не закрывай задачу по техническому PASS.
4. Остановись до ответа пользователя. Не опрашивай приёмку циклически и не начинай следующую задачу автоматически.

Минимальный итоговый комментарий:

> Результат: …
> Проверки: PASS / FAIL / NOT TESTED — …
> Ограничения: …
> Где проверить и что принять: …
> Статус: Wait, ожидает пользовательской приёмки.

## 7. Зафиксируй приёмку и продолжение

- После явной приёмки запиши подтверждение пользователя и поставь `done` только принятой задаче. Положительная оценка без ясного подтверждения приёмки не равна закрытию.
- Если принято несколько явно названных задач, закрой только этот перечень. Родитель и остальные подзадачи не закрываются автоматически.
- **Приёмка не разрешает merge, push, публикацию или удаление веток.** Это отдельные действия по запросу пользователя и правилам проекта.
- После перерыва перечитай актуальную задачу и последние существенные комментарии, сверь фактическое состояние работы. Не полагайся только на пересказ предыдущего чата и не повторяй уже подтверждённые действия.
- Если задача отмечена `done`, а объём новой доработки неясен, уточни его: не открывай принятую задачу заново и не начинай новую работу самовольно.
