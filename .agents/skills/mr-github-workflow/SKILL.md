# MR Studio / MR Live — облачная разработка из чата

Применяй только в режиме CLOUD из корневого [AGENTS.md](../../../AGENTS.md). Текущий чат с пользователем — источник задания, scope, решений, уточнений и приёмки; GitHub `vladleng/MR-Studio` — рабочий репозиторий. PR служит техническим средством проверки и интеграции, не отдельным трекером задач. В LOCAL используй `dsh-task-manager-workflow`. Полномочия определяет AGENTS.md, этот Skill их не расширяет.

## Вход в задачу

1. Возьми задание из текущего чата и учитывай уже согласованные решения и этапы. Не требуй номер Issue, не ищи задачу в Issues и не создавай записи в трекере как условие работы. Если пользователь прямо ссылается на историческую Issue, изучи только необходимое; создание, обновление, привязка и закрытие Issues — только по отдельному поручению.
2. Проверь доступные инструменты GitHub/gh/Git, фактические права, текущую ветку, HEAD, dirty diff и актуальный main. Если работа уже имеет ветку/PR, продолжай её без дублей. При недоступности инструмента фиксируй блокер, не имитируй действие.
3. Сопоставь задание с AGENTS.md, адресным кодом и тестами. Для версии используй [VERSIONING.md](../../../docs/VERSIONING.md); для CI — [CLOUD_DEVELOPMENT.md](../../../docs/CLOUD_DEVELOPMENT.md) и `mr-studio-build-test` только по необходимости.
4. Вопросы и аудит — только чтение. При порученной реализации определяй цель, scope, критерии приёмки и проверки по текущему заданию. Не создавай PLAN.md/PROGRESS.md, параллельный журнал или Issue для ведения текущей работы. Существенное расширение scope согласовывай.

## Ветка, реализация и PR

- Для новой порученной реализации используй тематическую ветку от актуального main. Сохраняй чужие и незакоммиченные правки; не выполняй reset, stash, смену существующей рабочей ветки или force-push без согласования.
- Реализуй только scope задания, проверь исходящий diff, коммить и публикуй тематическую ветку в рамках AGENTS.md. Не пушь напрямую в main.
- Открывай или обновляй один PR для соответствующего этапа. Укажи цель, версию, изменения, причины, сценарий воспроизведения (для багфикса), проверки и ограничения. Привязка к Issue и closing keywords не требуются; не добавляй их автоматически.
- Применяй независимые последовательности версий Studio и Live по VERSIONING.md; согласованные этапы/подэтапы определяются в чате. Не повышай версию только из-за PR, коммита, смены режима или неудачной сборки.
- Не публикуй SDK, секреты, пользовательские проекты, чувствительные логи и защищённые материалы.

## Проверки и готовность кандидата

- Выбирай минимально достаточный уровень L0–L4 и продукт Core/Studio/Live/Both по `mr-studio-build-test`. Для багфикса фиксируй RED → GREEN тем же сценарием либо обоснованные ручные шаги. Для документации и Skills — проверка текста, frontmatter, ссылок и diff без ручного запуска сборки приложения.
- Источник исполняемых правил CI — фактические `.github/workflows/` и `tools/ci/` текущей ветки. Проверяй доступность workflows, точный SHA кандидата, профиль, обязательные gates и реальные результаты; не выдумывай команды dispatch, не обходи gates и не дублируй их в Skill.
- Запускай только профильные проверки в рамках AGENTS.md; при FAIL изучай первую содержательную ошибку и повторяй затронутую проверку. Не отключай тесты ради PASS. При отсутствии обязательного workflow или артефакта фиксируй BLOCKED; Linux Core/GUI Compile не заменяют Windows Release.
- В чате и техническом описании PR фиксируй версию, ветку и SHA, ссылки на проверки и артефакты, PASS/FAIL/NOT TESTED, ограничения и необходимые ручные/аппаратные проверки. Не объявляй сборку или пакет готовыми без фактического подтверждения.

## Приёмка и интеграция

Техническая готовность и пользовательская приёмка — разные состояния. Передавай кандидат в чате с результатами и ссылками. Merge в main — только после явной пользовательской приёмки и согласования merge по AGENTS.md. Не включай auto-merge. Публикация GitHub Release — отдельное поручение.

После разрешённого merge проверь фактический HEAD main, версию и состояние PR; сообщи результат и ограничения в чате. Не считай интеграцию выполненной на основании одного запроса на merge.
