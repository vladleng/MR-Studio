# MR Studio / MR Live — Issue-first облачная разработка

Применяй только в режиме CLOUD из корневого [AGENTS.md](../../../AGENTS.md). GitHub Issues — основа разработки; текущий чат задаёт поручения, уточнения и явную приёмку пользователя. GitHub `vladleng/MR-Studio` — рабочий репозиторий. PR служит техническим средством проверки и интеграции, не отдельным трекером задач. В LOCAL используй `dsh-task-manager-workflow`. Полномочия определяет AGENTS.md, этот Skill их не расширяет.

## Вход в задачу

1. Найди назначенную или подходящую Issue до реализации; если её нет, создай краткую задачу в согласованном scope. Прочитай только нужную Issue, её реальные Sub-issues и связанные PR. Учитывай уточнения пользователя и кратко обновляй задачу; не дублируй существующие.
2. Проверь доступные инструменты GitHub/gh/Git, фактические права, текущую ветку, HEAD, dirty diff и актуальный main. Если работа уже имеет ветку/PR, продолжай её без дублей. При недоступности инструмента фиксируй блокер, не имитируй действие.
3. Сопоставь задание с AGENTS.md, адресным кодом и тестами. Для версии используй [VERSIONING.md](../../../docs/VERSIONING.md); для CI — [CLOUD_DEVELOPMENT.md](../../../docs/CLOUD_DEVELOPMENT.md) и `mr-studio-build-test` только по необходимости.
4. Вопросы и read-only аудит не требуют новой Issue. Для реализации соблюдай цель, scope и критерии задачи; существенное расширение согласовывай. Не создавай PLAN.md/PROGRESS.md или параллельный журнал.

## Задачи и настоящие Sub-issues

- Минимум Issue: цель, scope, критерии приёмки, при необходимости зависимости/ограничения. Краткий статус и ссылки после значимого этапа; не копируй технические детали PR, логи и историю чата.
- Самостоятельные подэтапы — только настоящие GitHub Sub-issues. В согласованном scope агент сам находит существующие и создаёт недостающие дочерние Issues, затем привязывает их к родителю и проверяет нативную связь. Если инструмент привязки/проверки недоступен, сначала создай недостающие Issues доступным инструментом, затем попроси пользователя выполнить только привязку/подтверждение в GitHub UI, с номерами и ссылками родителя и детей. Проси создать Issue вручную лишь при недоступности инструмента создания. Не заменяй связь чек-листом, текстовым Parent или «логическим» списком. Обычные ссылки зависимостей и критерии приёмки допустимы, но не являются подзадачами. Не начинай затронутый этап до подтверждения необходимой связи.
- Не дублируй, не переоткрывай принятую работу ради расширений. Закрывай принятые Sub-issues отдельно; родитель закрывается только после проверки обязательных настоящих детей и явной приёмки его scope.

## Ветка, реализация и PR

- Для новой порученной реализации используй тематическую ветку от актуального main. Сохраняй чужие и незакоммиченные правки; не выполняй reset, stash, смену существующей рабочей ветки или force-push без согласования.
- Реализуй только scope задания, проверь исходящий diff, коммить и публикуй тематическую ветку в рамках AGENTS.md. Не пушь напрямую в main.
- Открывай или обновляй один PR для соответствующего этапа. Укажи цель, версию, изменения, причины, сценарий воспроизведения (для багфикса), проверки и ограничения. Укажи ссылку `Refs #N` на соответствующую Issue; не используй closing keywords, которые могут автоматически закрыть задачу до отдельной приёмки.
- Применяй независимые последовательности версий Studio и Live по VERSIONING.md; согласованные этапы/подэтапы определяются Issue и её настоящими Sub-issues. Не повышай версию только из-за PR, коммита, смены режима или неудачной сборки.
- Не публикуй SDK, секреты, пользовательские проекты, чувствительные логи и защищённые материалы.

## Проверки и готовность кандидата

- Выбирай минимально достаточный уровень L0–L4 и продукт Core/Studio/Live/Both по `mr-studio-build-test`. Для багфикса фиксируй RED → GREEN тем же сценарием либо обоснованные ручные шаги. Для документации и Skills — проверка текста, frontmatter, ссылок и diff без ручного запуска сборки приложения.
- Источник исполняемых правил CI — фактические `.github/workflows/` и `tools/ci/` текущей ветки. Проверяй доступность workflows, точный SHA кандидата, профиль, обязательные gates и реальные результаты; не выдумывай команды dispatch, не обходи gates и не дублируй их в Skill.
- Перед объявлением BLOCKED для Windows-кандидата обязательно проверь предусмотренные проектом способы запуска в [CLOUD_DEVELOPMENT.md](../../../docs/CLOUD_DEVELOPMENT.md) и фактических `.github/workflows/` текущей ветки, включая альтернативные триггеры при недоступном workflow_dispatch. Ищи workflow по его объявленному имени и триггерам, а не только по имени файла. Отсутствие одного инструмента не означает отсутствия CI.
- Запускай только профильные проверки в рамках AGENTS.md; при FAIL изучай первую содержательную ошибку и повторяй затронутую проверку. Не отключай тесты ради PASS. При отсутствии обязательного workflow или артефакта фиксируй BLOCKED; Linux Core/GUI Compile не заменяют Windows Release.
- В техническом описании PR фиксируй версию, ветку и SHA, ссылки на проверки и артефакты, PASS/FAIL/NOT TESTED, ограничения и ручные/аппаратные проверки. В Issue — короткий статус, версия, ссылка на PR/проверки и остаток приёмки; в чате — кандидат и необходимые действия пользователя. Не объявляй сборку или пакет готовыми без фактического подтверждения.

## Приёмка и интеграция

Техническая готовность и пользовательская приёмка — разные состояния. Передавай кандидат в чате с результатами и ссылками. Merge в main — только после явной пользовательской приёмки и согласования merge по AGENTS.md. Не включай auto-merge. Публикация GitHub Release — отдельное поручение.

После разрешённого merge проверь фактический HEAD main, версию и состояние PR; кратко обнови Issue и сообщи результат в чате. Не считай интеграцию выполненной на основании запроса на merge. Закрытие Completed — только после явной приёмки и подтверждённого выполнения scope, без автоматического закрытия родителя.
