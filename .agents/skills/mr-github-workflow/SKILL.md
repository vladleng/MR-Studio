# MR Studio / MR Live — облачный журнал и GitHub workflow

Применяй только в режиме CLOUD из корневого [AGENTS.md](../../../AGENTS.md). GitHub `vladleng/MR-Studio` — рабочий репозиторий; Issues/Sub-issues — единственный активный журнал задач. В LOCAL используй `dsh-task-manager-workflow`, не веди два журнала. Полномочия определяет AGENTS.md, этот Skill их не расширяет.

## Вход и доказательства

1. Уточни назначенную Issue/Sub-issue по её номеру либо адресному поиску; прочитай актуальное тело, существенные комментарии, состояние, родителя и связанные PR по необходимости. Не обходи весь репозиторий и все Issues.
2. Проверь доступные инструменты GitHub/gh/Git, фактические права, текущую ветку, HEAD, dirty diff и актуальный main. Если задача уже имеет рабочую ветку/PR, продолжай её, не создавай дубль. При недоступности инструмента фиксируй блокер, не имитируй действие.
3. Сопоставь текущую задачу и принятые решения с AGENTS.md, кодом и тестами. Для версии адресно используй [VERSIONING.md](../../../docs/VERSIONING.md); для CI — [CLOUD_DEVELOPMENT.md](../../../docs/CLOUD_DEVELOPMENT.md) и `mr-studio-build-test` только при необходимости.
4. Вопросы и аудит — только чтение. В рамках назначенной реализации агент сам ведёт соответствующую Issue, комментарии и чек-лист. Не создавай параллельные PLAN.md/PROGRESS.md и не открывай новую Issue для исправления текущего этапа.

## Жизненный цикл задачи

- **Родительская Issue (этап):** общая цель, границы, подзадачи и критерии приёмки. Не закрывай автоматически при завершении отдельных подзадач.
- **Sub-issue:** самостоятельный срез с проверяемой приёмкой. Незначительное дополнение или багфикс оставляй в текущей задаче; значительное расширение scope согласовывай.
- **Тело задачи:** цель, контекст, scope/out of scope, критерии приёмки, профиль необходимых проверок, версия и связь с родителем. Обновляй только существенные результаты и блокеры; не отмечай непроверенные пункты выполненными.
- **Версия:** применяй независимые последовательности MR Studio и MR Live по VERSIONING.md. Номер Issue не равен номеру версии. Смена трекера, PR, коммит и неудачная сборка сами по себе версию не повышают.
- При переносе из DSH сохраняй ссылки/идентификаторы и фактические принятые этапы, не дублируй существующие Issues и не объявляй прежние результаты принятыми без подтверждения.

## Ветка, реализация и PR

- Для новой порученной реализации используй тематическую ветку от актуального main. Сохраняй чужие и незакоммиченные правки; не выполняй reset, stash, смену существующей рабочей ветки или force-push без согласования.
- Реализуй только scope задачи, проверь исходящий diff, коммить и публикуй тематическую ветку в рамках разрешений AGENTS.md. Не пушь напрямую в main.
- Открывай или обновляй один PR для соответствующего этапа: укажи Issue, версию, изменения, причины, сценарий воспроизведения, проверки и ограничения. До приёмки используй обычную ссылку на Issue, а не closing keyword, который может автоматически закрыть её при merge.
- Не публикуй SDK, секреты, пользовательские проекты, чувствительные логи и защищённые материалы в коде, Issues, PR или артефактах.

## Проверки и готовность кандидата

- Выбирай минимально достаточный уровень L0–L4 и продукт Core/Studio/Live/Both по `mr-studio-build-test`. Для багфикса фиксируй RED → GREEN тем же сценарием либо обоснованные ручные шаги. Для документации и Skills — проверка текста, frontmatter, ссылок и diff, без ручного запуска сборки приложения.
- Источник исполняемых правил CI — фактические `.github/workflows/` и `tools/ci/` текущей ветки. Проверяй доступность workflows, точный SHA кандидата, профиль, обязательные gates и реальные результаты; не выдумывай команды dispatch, не обходи gates и не дублируй их в Skill.
- Запускай только профильные проверки в рамках AGENTS.md; при FAIL изучай первую содержательную ошибку и повторяй затронутую проверку. Не отключай тесты ради PASS. При отсутствии обязательного workflow или артефакта фиксируй BLOCKED; Linux Core/GUI Compile не заменяют Windows Release.
- В Issue/PR фиксируй версию, ветку и SHA, ссылки на проверки и артефакты, PASS/FAIL/NOT TESTED, ограничения и необходимые ручные/аппаратные проверки. Не объявляй сборку или пакет готовыми без фактического подтверждения.

## Приёмка и интеграция

Техническая готовность и пользовательская приёмка — разные состояния. Передавай кандидат с результатами и ссылками; оставляй Issue открытой до явной приёмки. Merge в main и закрытие Issue — только после явной пользовательской приёмки и согласования этих операций по AGENTS.md. Не включай auto-merge и не закрывай родительскую задачу автоматически. Публикация GitHub Release — отдельное поручение.

После разрешённого merge проверь фактический HEAD main, версию, состояние PR и Issue; сообщи результат и оставшиеся ограничения. Не считай интеграцию выполненной на основании одного запроса на merge.
