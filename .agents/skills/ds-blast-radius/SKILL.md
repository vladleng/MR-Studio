# ds-blast-radius — оценка влияния изменений

**Когда применять:** изменение затрагивает общий компонент, контракт API/формата, потокобезопасность, асинхронный lifecycle, plugin hosting или есть конкретный риск скрытой регрессии. Для локальной косметической правки без поведения отдельный анализ обычно не нужен.

1. **Ограничь область.** Прочитай цель задачи, текущий diff и связанные вызовы/потребителей. Не сканируй весь репозиторий без признаков необходимости.
2. **Найди до трёх ключевых рисков.** Проверяй реальные границы: MR Studio ↔ MR Live ↔ Shared Core; GUI ↔ Commands/Model; Undo/Redo и сохранение проекта; audio callback/RT, PDC, MIDI/Transport, plugin/editor lifetime, ARA2 — **только если они затронуты**.
3. **Проверь критичное утверждение о безопасности.** Укажи подтверждение кодом/тестом либо выполни самый дешёвый адресный тест, когда он доступен. Не требуй запуска приложения или полного CTest ради формального достижения уровня доказательства. Выбор L0–L4 и проверок — по проектному Build/Test Skill.
4. **Дай короткое заключение:** что может сломаться, какой факт подтверждён, какой остаётся `NOT TESTED`, какие точечные проверки нужны. При выявленной регрессии приложи воспроизведение и передай исправление в обычный процесс задачи.

**Границы:** это анализ, не разрешение на рефакторинг, расширение scope, изменение задач, запуск релиза или публикацию. Не меняй код в рамках самостоятельного вызова Skill, если исправление явно не поручено. Не подключай другие `ds-*` и субагентов автоматически.
