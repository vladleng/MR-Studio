# ds-review-loop — ревью по риску, без обязательных циклов

**Когда применять:** пользователь просит ревью или сложность/риск изменения оправдывает дополнительную проверку (общий Core, RT, сохранение проектов, публичные интерфейсы, большой diff). Для обычной небольшой правки достаточно предусмотренных проектом тестов и контроля diff.

1. **Установи границы:** цель, разрешённый scope, текущие `git status`, HEAD и diff. Для локальных MR Studio/MR Live используй фактическую рабочую ветку, а не предположительный удалённый `main`; сохрани посторонние изменения.
2. **Проверь реализацию по существу:** дефекты, недостающие проверки, нарушенные инварианты, затронутых потребителей, не относящийся к задаче код. Не требуй нового дизайна и не придирайся к стилю без функциональной причины.
3. **Независимое ревью — опционально.** Если оно существенно полезнее самопроверки и доступно в DSH, привлеки **не более одного** read-only reviewer с чёткой целью, путями, ограничениями и известными результатами. Не запускай вложенных субагентов. Использование более дорогой модели — только после согласования пользователя. Если reviewer недоступен, выполни собственную проверку и честно обозначь её как self-review.
4. **Разбери замечания:** `blocker` — нарушена цель или безопасность; `important` — подтверждённая регрессия; `minor` — необязательное улучшение. Для каждого существенного замечания укажи файл/факт и минимальную проверку. Не расширяй задачу ради пожеланий reviewer.
5. **Исправления и повтор:** если в пределах уже разрешённой реализации — внеси минимальное исправление и повтори только затронутые проверки; при чистом запросе «аудит/ревью» **не меняй файлы**. Дополнительный раунд проводи лишь после существенной правки или спорного факта, не ради формального APPROVE. Не делай бесконечный review loop.

**Результат:** кратко укажи `PASS / CHANGES NEEDED / NOT VERIFIED`, существенные находки, реально запущенные проверки и пробелы. Review не заменяет пользовательскую приёмку. Для MR Studio/Live не создавай PR, не выполняй merge/push и не запускай Actions по инициативе Skill. Записи в DSH Task Manager — только в пределах полномочий проекта; отдельный review ledger/документ не создавай. Не вызывай другие `ds-*` автоматически.
