# MR Studio: общие инструкции разработки

## Начало нового чата

1. Прочитай [актуальный контекст](docs/PROJECT_CONTEXT.md) и
   [политику локальной разработки](docs/LOCAL_BUILD_POLICY.md).
2. Проверь `git status --short`, текущую ветку и последние коммиты. Сохрани чужие
   незавершённые изменения; не переключай ветку и не сбрасывай checkout автоматически.
3. Открой документы по запрошенной области. Для движка обязательны
   `docs/ENGINE_PERFORMANCE_PLAN.md` и `docs/PROCESSING_RELIABILITY.md`.
4. Кратко обозначь пользователю текущую задачу и продолжай её выполнение.
   Не начинай следующий этап только потому, что он указан в roadmap.

Текущие инструкции пользователя уточняют или заменяют проектные договорённости.
Исторические записи в README/START_HERE/checklists не переопределяют более позднюю
приёмку в PROJECT_CONTEXT и тематических документах. При расхождении проверь код,
дату и свидетельство приёмки, а не угадывай статус по имени сборки.

## Продукт и архитектура

- Moon River Studio / MR Studio — одна DAW. Live Mode — встроенный режим того же
  приложения, проекта и движка, а не самостоятельный продукт. Исторические названия
  MR Live и отдельные технические targets не меняют этой продуктовой границы.
- Общий Core обслуживает Arrange, Edit, Mix и будущий Live. UI обращается через
  Application/Commands; изменения модели учитывают Undo/Redo и сохранение проекта.
- Активная платформа — Windows, интерфейс JUCE/C++, звук ASIO. Другие платформы
  и собственные эффекты/инструменты не входят в текущий этап оптимизации.
- Строим универсальный движок. Не вводи оптимизацию по имени проекта, бренду
  плагина или пресету. Fender Studio Pro — ориентир эффективности, а не доказанная
  достигнутая эквивалентность. Измерения callback time не равны общей загрузке CPU.

## Рабочие договорённости

- Код, source-коммиты, configure/build/tests и пакеты остаются локально.
  GitHub используется только для issues и документации. Нельзя отправлять ветку
  с локальным кодом ради документации; обновляй только выбранные doc-файлы.
  Документальные GitHub-коммиты помечай `[skip ci]`. GitHub Actions не запускать.
  Code push/PR/merge требуют отдельного прямого запроса пользователя.
- Используй существующий checkout и toolchain. Старые сборки сохраняй, новую
  выпускай в отдельной папке с точной версией. Не меняй пользовательские проекты
  и настройки ради теста; для регрессий используй временные файлы и fixtures.
- Общайся по-русски, кратко сообщай результат, проверки и конкретные ограничения.
  Не проси повторного разрешения на уже согласованную локальную работу.
- Приёмка исправления не означает приёмку всего parent-этапа. Закрывай issue
  только в принятом пользователем объёме, с пройденными необходимыми проверками.
- Не повторяй специальные installed TH-U/Nuro state/editor/DSP проверки на каждом
  билде: они приняты. Повтор нужен по запросу или новой проблеме именно этих плагинов.
  Обычные синтетические VST3-регрессии сохраняются.

## Harma Waves Native — только по запросу

- Направление планирования: [#115](https://github.com/vladleng/MR-Studio/issues/115). Если пользователь поручил Harma Waves/Smart Voicing внутри MR Studio, сначала прочитай [архитектуру](docs/HARMA_WAVES_NATIVE.md), [roadmap](docs/HARMA_WAVES_ROADMAP.md), [Codex handoff](docs/HARMA_WAVES_CODEX_HANDOFF.md), затем конкретный issue #116–#127 и исходную принятую документацию Smart-Voicing.
- Первый slice — аудит/перенос host-neutral Core Smart-Voicing stable 0.5, без переписывания правил и **без преждевременного нового Voice Leading**. Native MRS не равен VST3/ARA adapter. Не путать Smart-Voicing с отдельным Smart-Improviser.
- Никакая из новых задач Harma Waves не считается реализованной/принятой в MRS по факту успешного Smart-Voicing CI. Актуальный MRS Stage 5/#25 сохраняет собственные зависимости. Не переключай активный roadmap без прямого запроса пользователя.
- GitHub issue links/checklists не являются native GitHub sub-issues: проверяй фактические parent links до заявлений о процентах прогресса.

## Реализация и проверка

- Применяй подходящие навыки из рабочей папки чатов `.codex/skills/` (путь в контексте):
  `mr-feature-implementation`, `mr-realtime-audio-safety`,
  `mr-studio-ui-design-system`, `mr-studio-build-test`. Читай нужный SKILL.md,
  а не все навыки при каждом старте.
- RT: никаких новых host allocation/locks/I/O/UI calls в callback; один владелец
  состояния DSP/плагина. Останавливай и присоединяй обработчики до замены/уничтожения
  графа. Сохраняй PDC, transport context, raw recording и plugin state/editor lifetime.
- Новая функция должна проходить через нужные слои: UI, commands/model, engine,
  Undo, persistence, compatibility. Для временного UI-состояния явно укажи,
  что оно не сохраняется в проект. Не создавай новую схему без необходимости.
- UI развивай в действующей теме и компонентах. Сохраняй принятые взаимодействия;
  проверяй размеры, DPI и состояния изменённых элементов.
- Проверяй соразмерно изменению: для кода — сборка и затронутые тесты, для
  hosting/RT — соответствующие регрессии и GUI smoke. Документация не требует
  пересборки приложения. Реальную ASIO/визуальную приёмку не подменяй offline PASS.
- Текст сохраняй явно в UTF-8, без двойных CRLF. Перед фиксацией проверь diff.

## Передача контекста

После завершённой функции, исправления, приёмки или остановки незавершённой работы
обнови `docs/PROJECT_CONTEXT.md`: дата, задача/issue, сделанное, оставшееся, source
commit/ветка, пакет, проверки, точная пользовательская приёмка и следующий шаг.
Для незавершённой работы перечисли изменённые файлы, ошибки и безопасное продолжение.
Сохраняй там короткий текущий снимок; детали и историю оставляй в тематических docs.
Не записывай предполагаемые результаты как факты. Существующий пакет с хешами
не переписывай задним числом ради новой записи о приёмке.
