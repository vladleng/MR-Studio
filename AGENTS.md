# MR Studio — правила агентов (Issue-first)

Постоянные правила для всех харнесов. Читай только документы, необходимые текущей задаче.

## Источники истины и полномочия

- Разработка, исходники, правила, спецификации, Git, сборки и артефакты хранятся локально на Windows-ПК. GitHub используется для Issues и обсуждения задач. Это действующий процесс от 2026-11-16; прежние разрешения на облачную разработку, push и CI не действуют.
- Локальный checkout показывает фактическую реализацию; назначенная Issue — требования, статус и приёмку. Не заменяй локальный код опубликованной веткой; старые PR/Actions и памятки не подтверждают текущую реализацию.
- Приоритет проектных инструкций: текущий запрос пользователя → `AGENTS.md` → актуальная Issue/подтверждённая приёмка → каноническая спецификация и профильные `mr-*` skills → универсальные `ds-*` skills. Неразрешённый конфликт, влияющий на результат, уточни; независимую работу продолжай. Skills не расширяют полномочия.
- Push исходников/правил, создание PR, запуск Actions и публикация пакетов требуют отдельного запроса. Merge в локальный `main` требует отдельного явного разрешения; PASS проверок и приёмка сами по себе его не разрешают. Существующие workflows не менять и не удалять вне порученной задачи.
- Выполняй только порученный этап; не начинай следующий автоматически. Не требуй повторного разрешения на уже согласованную работу.

## Старт и навигация

1. Если назначена Issue, прочитай её критерии и нужные фрагменты связанных документов. Без Issue выполняй конкретный запрос; не требуй её создания ради разовой проверки или правки.
2. Перед изменениями проверь `git status --short`, ветку, HEAD и имеющийся diff. Работай в назначенной тематической ветке; сохраняй чужие изменения. Не делай reset, stash или branch switch без согласования.
3. Ищи по классу, функции или номеру Issue; читай нужный диапазон. Не загружай весь `docs/`, все Issues/skills и большие документы по умолчанию; не перечитывай неизменённое.
4. Для навигации используй `docs/START_HERE.md`. `docs/SESSION_CONTEXT.md` — памятка, не статус; `.codex/hooks.json` лишь помогает её загрузить. `docs/README.md` — тематический индекс, `docs/PROJECT_CONTEXT.md` — короткий указатель.

`AGENTS.md` — общий вход; `CLAUDE.md` и `GEMINI.md` только импортируют его. Канонические skills находятся в `.agents/skills/`; `.codex/skills` — необязательная ссылка совместимости. Если харнес не обнаруживает skill, прочитай его файл напрямую.

| Задача | Обязательный профильный вход; читать только нужные разделы |
| --- | --- |
| GitHub Issues, включая DSH | `.agents/skills/mr-github-workflow/SKILL.md`; реальные `gh` или connector/API |
| GUI, SVG, иконки | `.agents/skills/mr-unified-gui/SKILL.md`, `docs/MR_UNIFIED_DESIGN_SYSTEM.md`; если skill отсутствует, проверить локальную историю Git |
| Audio callback, граф, hosting, RT | `.agents/skills/mr-realtime-audio-safety/SKILL.md`, релевантные разделы `docs/ENGINE_PERFORMANCE_PLAN.md` и `docs/PROCESSING_RELIABILITY.md` |
| Сборка, тесты, пакет | `.agents/skills/mr-studio-build-test/SKILL.md`, `docs/LOCAL_BUILD_POLICY.md` |
| Назначение версии, подготовка билда | [docs/VERSIONING.md](docs/VERSIONING.md): схема `0.I.S`, независимые версии Studio/Live, суффиксы и единая версия приложения/пакета; выпущенные версии не переименовывать |

## Сохранность и локальное хранение

- В Git хранятся исходники, тесты, ресурсы, конфигурации, документация и skills. Сборки, SDK, кэши и логи — в исключённых из Git каталогах `build/` или явно выбранном каталоге вне checkout. Установленные инструменты Windows находятся вне checkout; версии SDK закрепляются проектом.
- Сохраняй существующие SDK, сборки, пользовательские проекты, настройки, WAV/NAM и незафиксированные файлы; не удаляй, не перезаписывай и не публикуй их. Fixtures создавай отдельно. Исходники и историю Git необходимо резервировать отдельно от ПК; Issues не заменяют резервную копию.
- Пакеты для пользовательской/аппаратной приёмки готовь в рамках соответствующего запроса и размещай отдельно вне checkout; принятые версии сохраняй. Установку инструментов/SDK не инициируй вследствие правки документации.
- SDK, секреты и проприетарные плагины не публикуй. Защищённые сторонние материалы не добавляй в репозиторий/пакеты без прав и разрешения; веса не включай в базовый installer. Не объявляй юридическую проверку выполненной без её проведения.

## Архитектура и безопасность

- MR Studio — DAW, MR Live — отдельное Windows/JUCE/ASIO приложение, запускаемое с Home, с документом `.mrlive`. Они используют общий Core, Engine/ASIO/Transport/Model/GraphStore/MIDI/plugin host; второй backend не создавать. Прямое открытие Studio-песни через Live item и переход в Studio не входят в Live workflow; Studio → Live Playback — отдельная будущая функция экспорта. Контракт: `docs/MR_LIVE_NATIVE_INTEGRATION.md`.
- Изменения проводи через принятые Commands/Model. Сохраняй Undo/Redo, persistence, plugin/editor lifetime, PDC, transport и raw recording. Миграции формата — только при обоснованной необходимости.
- **Audio callback:** никаких новых alloc/free, mutex/locks, disk/network I/O или UI calls. Decode IR/NAM, подготовка эффектов и пересборка графа — вне callback; обеспечивай безопасный lifecycle и переключение без двойного аудиотракта. RT подтверждай callback/xrun измерениями; 128 сэмплов не обязательны для всех студийных эффектов.
- GUI всей MR Studio/Live и native plugins следует MR UDS: dark blue-graphite, flat, тонкая светлая SVG-контурная графика. Изменяй только порученный объём; принятые экраны/`ui::Theme` остаются as-built до согласованной миграции. Не меняй DSP и сторонние VST3 GUI ради оформления. Правила библиотеки assets и генераторов — в `mr-unified-gui`.
- Соблюдай существующие паттерны ошибок, логирования и архитектуры. Не создавай параллельные механизмы, абстракции «на будущее» и новые зависимости без согласования; необходимость зависимости обоснуй в назначенной Issue, а при её отсутствии — в чате.
- **ARA2 ON для Studio; Live standalone всегда без ARA2**, ARA SDK/scanner не входят в Live-пакет. В совместной сборке ARA2 только в Studio. Studio ARA OFF — лишь по явно запрошенной диагностике. Studio-only использует `MRS_BUILD_LIVE=OFF`; Live-проверки добавляй только при конкретном влиянии на Live, сохраняя нужные общие Core-проверки.

## Проверки по типу изменения

Необходимые адресные локальные сборки и тесты входят в порученную реализацию кода и не требуют повторного разрешения, если пользователь не ограничил проверки. «Учесть в следующем билде» само по себе не поручает выпуск отдельного пакета. Команды/targets/presets определяй по текущим локальным скриптам и CMake, не по историческим workflows.

Уровень проверки L0–L4 и косметическое исключение выбираются по `.agents/skills/mr-studio-build-test/SKILL.md` и `docs/LOCAL_BUILD_POLICY.md`. Полный CTest (L4) — только для отдельно согласованного кандидата либо при обоснованной необходимости; основание указывай в отчёте.

Косметическое исключение действует только без изменений поведения, геометрии, hit areas, layout, bindings, модели, Undo/persistence, DSP, зависимостей и конфигурации сборки; оно имеет приоритет над прежними V1/L1 требованиями skills. Не запускай массовые DPI-проверки, упаковку, смену ярлыков или специальные TH-U/Nuro проверки без соответствующей задачи/проблемы; синтетические VST3 тесты сохраняются.

## Багфиксы и диагностика

1. **RED:** до исправления создай/выбери регрессионный тест и запусти на неисправленном коде. Подтверди падение именно из-за исследуемой ошибки, а не среды.
2. **GREEN:** внеси минимальное исправление и повтори тот же тест; сохрани его для предотвращения регрессии.
3. Если автоматическое воспроизведение объективно невозможно или непропорционально сложно (GUI/RT/оборудование), до правки запиши точные шаги и наблюдаемый результат; после повтори их. По возможности автоматизируй проверяемую часть. Невыполненную аппаратную проверку отмечай **NOT TESTED** до фактической проверки пользователем.
4. Не удаляй, не отключай и не ослабляй тесты/ассерты ради PASS. Корректировка допустима лишь при согласованном изменении требований или доказанной ошибке теста; причину укажи в отчёте и, если создаётся, PR.
5. При FAIL прочитай конкретный лог и проверь новую гипотезу до повторной сборки. После трёх безрезультатных попыток одной ошибки останови изменения наугад; запиши наблюдения, проверенные гипотезы и следующий диагностический шаг. Продолжай лишь с новой обоснованной гипотезой/данными; если нужен ввод пользователя, сообщи о блокере.

## Документация, отчёт и приёмка

- `docs/` хранит долговременные технические контракты. Сначала ищи существующий тематический документ; новый создавай лишь при необходимости. Изменяй спецификацию при изменении контракта; различай implemented/planned/historical. Перед удалением/консолидацией проверь уникальные требования и входящие ссылки, перенеси актуальное и исправь ссылки.
- ТЗ, этапы, результаты и приёмка относятся к Issue, не к параллельным журналам в `docs/`. `ds-plan-loop`, `ds-ledger`, `ds-context-reset` не должны автоматически создавать `PLAN.md`/`PROGRESS.md`. Markdown-чеклисты не являются native Sub-issues; не заявляй проценты без проверки иерархии.
- **Создание Issue/Sub-issue:** только по явному поручению; критерии, формат тела, native-привязка, проверка иерархии и порядок закрытия — `.agents/skills/mr-github-workflow/SKILL.md` (раздел Issue / Sub-issue lifecycle).
- **Уровень задачи:** третья цифра версии — порядковый номер Sub-issue; новая Sub-issue нужна для независимого среза с собственной приёмкой или значительного дополнения, мелкий follow-up — `-UpdN`/комментарий в текущей Issue (`docs/VERSIONING.md`).
- **Обновление Issue:** если оно входит в поручение, фиксируй там содержательные результаты и блокеры через доступный API/`gh`; иначе достаточно отчёта в чате. Назначение Issue как источника требований само по себе не поручает публикацию комментариев. Недоступность GitHub не останавливает независимую локальную работу; честно отметь непереданные результаты.
- Перед завершением проверь scope diff и выполнение обязательных проверок. В отчёте кратко укажи результат, ветку/HEAD и dirty state для разработки, команды/конфигурацию и фактические PASS/FAIL/NOT TESTED, ограничения, commit/пакет при наличии. Для багфикса обязательны **RED / GREEN / REGRESSION / NOT TESTED**; для отдельно запрошенного PR — также причина и способ воспроизведения/проверки.
- Разделяй «код реализован», «проверки PASS» и «пользовательская приёмка». Без проверки исходного репро не объявляй баг исправленным; при обязательном FAIL/NOT TESTED не объявляй этап полностью проверенным. PASS другой ревизии не подтверждает текущий код; автоматические проверки не доказывают слуховую оценку и физические ASIO/DPI характеристики.
- После явной пользовательской приёмки закрывай соответствующую Issue/Sub-issue как **Closed → Completed**; это не требует merge и не разрешает его.
- Правки правил согласуй между `AGENTS.md`, затронутыми skills и входными ссылками. При фиксации выделяй их в отдельный локальный docs-only коммит; код приложения и пользовательские файлы в него не включай. В тематическую ветку разработки включай необходимые docs/skills/assets.
- Отвечай по-русски и кратко: результат, проверки, ограничения, следующий шаг. Большие логи оставляй локально вне Git.
