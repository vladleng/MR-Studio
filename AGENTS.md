# MR Studio — инструкции для Codex (Issue-first)

Цель: безопасная локальная разработка MR Studio **без лишнего чтения контекста**.
Это короткие постоянные правила, а не история проекта.

## 1. Источник истины

- **GitHub `main`:** эталонные версии `AGENTS.md`, тематической документации и GitHub Issues (ТЗ, этапы, статус, приёмка). **Локальный `AGENTS.md` — действующие инструкции для локального Codex** до их синхронизации. При необходимости проверить версию; не скачивать весь `docs/` на каждый старт.
- **Локальный checkout:** фактический исходный код, незакоммиченные изменения, сборки и результаты тестов. Код может опережать GitHub. Документ или Issue не доказывает, что функция уже работает; локальный код не доказывает пользовательскую приёмку.
- При конфликте: **текущий запрос пользователя → актуальный Issue и подтверждённая приёмка → каноническая тематическая спецификация**; историю/старые сводки использовать только как справку. Если статус, API или реализация противоречат друг другу — проверить точечно и сообщить пользователю; не подменять реальность текстом.
- Markdown-ссылки и чеклисты **не равны** нативным GitHub Sub-issues. Процент прогресса заявлять только по проверенной иерархии.

## 2. Начало задачи: минимум токенов

1. Определи **конкретный Issue/запрос и границы этапа**. Прочитай его описание, критерии приёмки и **только необходимые разделы** документов, на которые он ссылается.
2. Перед изменением локального кода проверь `git status --short`, ветку и HEAD; не затирай чужие изменения, не делай reset/stash/switch branch автоматически.
3. Найди нужные исходники и контракты **поискoм и выборочным чтением**. Сначала точечный поиск, затем нужный диапазон строк; не открывай большие файлы целиком без причины.
4. **Не читать целиком по умолчанию** `docs/PROJECT_CONTEXT.md`, `docs/LOCAL_BUILD_POLICY.md`, `docs/ROADMAP.md`, весь `docs/`, все Issues и все skills. Когда нужно уточнить состояние — ищи по номеру Issue/имени функции, прочитай свежий раздел и при необходимости соответствующее свидетельство. Большие устаревшие разделы не считать текущим ТЗ.
5. Прочитай только относящийся к задаче `SKILL.md` из `.codex/skills/`, если навык реально помогает. Для изменений RT/аудиографа обязательны **релевантные** правила безопасности; для сборки — **релевантные** части build policy. Не отменяй безопасность ради экономии токенов.
6. В одном рабочем контексте **не перечитывай неизменившиеся документы**. Если данных не хватает или версии различаются, запроси/прочитай конкретный участок. Кратко зафиксируй план и выполняй согласованный объём; следующий stage автоматически не начинай.

Для MR Rig ориентируйся на [#197](https://github.com/vladleng/MR-Studio/issues/197) и **назначенный** sub-issue; для MR Cab — на [#182](https://github.com/vladleng/MR-Studio/issues/182). Не загружай весь набор их документов, если текущему этапу нужен только один. Для других направлений действуют их Issue/тематические docs, без специальных блоков в этом файле.

## 3. Неподвижные архитектурные ограничения

- MR Studio — **одна** DAW с общим Core для Arrange/Edit/Mix и встроенного Live Mode (не отдельное приложение). Windows / JUCE C++ / ASIO — действующая платформа.
- UI меняет состояние через принятые Commands/Model; сохраняй Undo/Redo, project persistence, plugin/host state, editor lifetime, transport и PDC. Новые схемы и миграции — только с доказанной необходимостью и проверкой совместимости.
- Аудиопоток realtime: **никаких новых allocations/free, locks, disk/network I/O и UI calls в audio callback**. Подготовка IR/NAM/плагинов и перестройка графа — вне callback, безопасное переключение состояния и завершение worker/lifetime. Не создавай второй аудиодвижок или несанкционированные аудиомаршруты.
- **Live/запись и Studio/mixing имеют разные требования к буферу и задержке.** 128 сэмплов не обязательны для всех студийных эффектов. Производительность подтверждай измерениями callback/xrun, а не только общей загрузкой CPU.
- Для изменений движка читай нужные места `docs/ENGINE_PERFORMANCE_PLAN.md` и `docs/PROCESSING_RELIABILITY.md`, а также RT-safety skill. UI придерживается текущей принятой темы; MR UI Kit применяй, когда он готов и это входит в задачу.

## 4. Где выполнять работу и как проверять

- **Код, локальные source-коммиты, configure/build, тесты, пакеты и проверка оборудования — только в локальном checkout.** Сохраняй старые принятые пакеты; тестовые проекты, пользовательские IR/NAM и настройки не изменяй без разрешения.
- **На GitHub разрешены документы и Issues** по текущей работе; docs-only commits на актуальный `main` с `[skip ci]`, с проверкой конфликта обновлений. **Не запускать GitHub Actions, не пушить source, не создавать PR/merge** без прямого запроса пользователя.
- Для изменения кода: целевые тесты и сборка; для аудиографа/host/RT — затронутые регрессии, PDC и GUI smoke. Полный текущий набор тестов — на согласованной кандидатной сборке/выпуске, а не на каждом мелком исправлении. **Docs-only правки не требуют сборки.** Указывай, что реально TESTED и что NOT TESTED (особенно физический ASIO, слуховая и DPI-приёмка).
- Общие синтетические VST3 тесты сохраняются. Не гоняй ранее принятые специальные installed TH-U/Nuro проверки без относящейся к ним новой проблемы или запроса.
- Проверяй diff перед фиксацией; текст UTF-8, без удвоения CRLF; без скрытых изменений пользовательских файлов.

## 5. Статус, приёмка и передача

- Разрабатывай **только назначенный этап**; следующее issue или stage — после отдельной команды. Предыдущая приёмка частичной функции не означает приёмку всего parent.
- После значимого этапа/исправления обнови **его Issue**: факт реализации, local branch/commit, результаты проверок, ограничения, готовность к ручной приёмке и следующий шаг. Закрывай только после подтверждённой приёмки в соответствующем объёме.
- Тематическую документацию GitHub обновляй **только при реальном изменении контракта**. `PROJECT_CONTEXT.md` — краткая сводка/указатель при необходимости, **не обязательный журнал каждого сообщения и не обязательное чтение целиком**. Детальные логи и историю храни в отчётах по задачам, а не дублируй в нескольких документах.
- Общайся с пользователем по-русски. В ответе — коротко: что изменено, какие тесты фактически проведены, что осталось и где отчёт; не вставляй многостраничные логи в чат.

**Главный принцип:** `Issue → нужная спецификация → конкретный код → локальные проверки → отчёт в Issue`. Не загружай весь проект в контекст ради одной задачи.
