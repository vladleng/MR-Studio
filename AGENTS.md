# MR Studio — правила агентов (Issue-first)

Этот файл содержит **только постоянные правила**. Не загружай всю документацию проекта ради одной задачи.

## Вход для разных харнесов

- `AGENTS.md` — общие правила для всех агентов. `CLAUDE.md` и `GEMINI.md` импортируют этот файл; не создавай в них отдельные копии правил.
- Канонические проектные skills — `.agents/skills/<name>/SKILL.md` вместе с их references/assets. Выбирай только применимые skills по задаче; если харнес не обнаруживает каталог автоматически, читай нужный `SKILL.md` как обычный файл. Локальная `.codex/skills` — необязательная ссылка совместимости, не источник и не часть облачной настройки.
- В облаке начинай с актуального GitHub `main` либо назначенной тематической ветки и проверяй её HEAD. Локальные непереданные коммиты, файлы, Windows-пути и установленные SDK не появляются в облачной среде автоматически. Подготовка и проверки — по `docs/CLOUD_DEVELOPMENT.md` и workflow текущей ветки.
- Для навигации используй `docs/START_HERE.md`; `docs/SESSION_CONTEXT.md` — короткая памятка, а не статус задач. Codex hook `.codex/hooks.json` — дополнительный механизм загрузки этой памятки; другим харнесам он не требуется.

## Среда разработки и публикация

**Решение пользователя 2026-11-08: разработка ведётся онлайн, GitHub — источник истины.** Основная среда — онлайн-работа с репозиторием: `main` хранит правила, спецификации и Issues, тематические ветки — актуальный код. Windows-сборки, тесты и артефакты выполняются GitHub Actions по согласованным профилям.

Локальный Windows-ПК используется для пользовательской приёмки, аппаратных ASIO/MIDI/DPI/vendor проверок и запуска собранных артефактов; локальные сборки допустимы, но не являются источником истины. Source commits/push в тематических ветках разрешены; merge в `main` — только после отдельной пользовательской приёмки. Текущие принятые версии: **MR Studio 0.10.2-fix5** и **MR Live 0.9.2**; обе принятые линии объединены в `main`.

**ARA2 ON по умолчанию для MR Studio**, но **MR Live standalone всегда без ARA2** (`checks=live`: ARA OFF, без ARA SDK/scanner в Live-артефакте; при совместной сборке Studio+Live ARA есть только в Studio). Для Studio ARA OFF допускается только как явно запрошенная диагностическая сборка; полный CTest — отдельно. См. #303 и `docs/MR_LIVE_NATIVE_INTEGRATION.md`. Аппаратные ASIO/MIDI/DPI/vendor проверки выполняются локально и отмечаются по фактическому результату.

SDK/секреты/проприетарные плагины не публиковать. Пользовательские проекты/настройки/WAV/NAM и принятые локальные сборки не менять и не публиковать; fixtures создавать отдельно. Сторонние защищённые материалы не добавлять в репозиторий или пакеты без прав и разрешения. Процесс сборки — `.agents/skills/mr-studio-build-test/SKILL.md`; `docs/CLOUD_DEVELOPMENT.md` описывает действующий онлайн-процесс, `docs/LOCAL_BUILD_POLICY.md` — историческая справка.

**Локальная приёмка (Windows):** артефакты раскладываются в отдельную папку вне checkout и запускаются оттуда; для бинарников внутри checkout действует ограничение записи только внутри него, поэтому запуск из `build/` может ломать сохранение проектов и журналы диагностики. Проверено 2026-11-08: копия runtime вне checkout пишет в `Documents\MR Studio` нормально.

## Источники истины

- **GitHub `main` — источник истины** для правил, спецификаций и статуса работ (решение пользователя 2026-11-08). Правила редактируются в `main` docs-only коммитом с `[skip ci]` либо через PR; локальная копия `AGENTS.md` — рабочая копия и не может отменять опубликованное решение. `AGENTS.md` текущей ветки определяет работу в задаче с учётом инструкций среды и текущего запроса.
- **Локальные правки правил:** если правило меняется локально, его нужно вернуть в `main` (docs-only коммит с `[skip ci]` или PR), а не оставлять только в checkout. В отдельный коммит правил включай `AGENTS.md`, изменённые `.agents/skills/**` и необходимые входные файлы харнесов/ссылки документации; исходный код приложения, сборки и пользовательские файлы в такой коммит не попадают. Изменения механизмов запуска проверяй отдельно по их фактическому объёму.
- **Issues** — отдельный источник ТЗ, статусов и приёмки, не часть ветки. Проверяй расхождения **точечно**, только когда они влияют на задачу.
- **Checkout задачи** — фактический код, незавершённые изменения, сборки и результаты тестов; он может опережать GitHub. Issue не доказывает, что код реализован; код/тесты не доказывают пользовательскую приёмку.
- Для проектных решений: **текущий запрос пользователя → актуальный Issue/подтверждённая приёмка → каноническая спецификация**. Старые roadmap, сводки и handoff — справка, не замена новых решений. Если конфликт не разрешается этим порядком и влияет на результат, уточни спорный пункт; независимую работу продолжай.
- Markdown-чеклисты не являются нативными GitHub Sub-issues; не заявляй проценты прогресса без проверки реальной иерархии.

## Политика технической документации

- `docs/` хранит **долговременные технические контракты**, применимые к нескольким задачам или компонентам и необходимые после закрытия Issue. Новый Markdown-файл создавай только при этой необходимости; прежде проверяй существующий тематический контракт.
- **ТЗ, подэтапы, чек-листы, версии промежуточных сборок, результаты тестов, исправлений и приёмку** фиксируй в назначенной GitHub Issue/Sub-issue, PR и Actions, а не во втором журнале в `docs/`.
- Меняй существующую спецификацию только при изменении её технического контракта. Различай **implemented**, **planned** и **historical** по коду и принятому scope; не копируй «текущий статус» в несколько Markdown-файлов.
- `docs/README.md` — индекс по темам, `docs/PROJECT_CONTEXT.md` — короткий указатель, не handoff/хронология. Старые `Stage/FIX/UPD` документы и Git history не переопределяют `AGENTS.md`/актуальные Issues.
- Перед консолидацией, архивированием и удалением проверяй **уникальные технические требования и ссылки** из `AGENTS.md`, Skills, действующих Issues и иных документов; сначала перенеси актуальные контракты, затем исправь входящие ссылки.
- Для docs-only изменений достаточно проверки diff, структуры ссылок и непротиворечивости; сборку приложения не запускать без технической причины. Merge — только после приёмки пользователя.

## Правила версирования для сборок, Issues и Sub-issues

Единая схема для соответствующей линии разработки: **`0.I.S`** (например, `0.8.8`).

- **Первая цифра** (`0`) — основной этап разработки; меняется только по отдельному согласованному решению.
- **Вторая цифра** (`I`) — номер этапа родительской Issue; увеличивается **только при старте следующей родительской Issue**, не при исправлениях, коммитах, PR или сборках. Пример: `0.8.0 → 0.9.0`.
- **Третья цифра** (`S`) — порядковый номер Sub-issue в текущей родительской Issue: `0.8.1`, `0.8.2`, …; при переходе к новой родительской Issue сбрасывается в `0`. Если Sub-issues нет, используется версия `0.8.0`.
- **Исправление ошибки** текущей версии — суффикс `-fix1`, `-fix2`, … (например, `0.8.8-fix1`). Ошибки и регрессии не увеличивают базовую версию.
- **Небольшое дополнение** в рамках той же Sub-issue — суффикс `-Upd1`, `-Upd2`, … (например, `0.8.8-Upd1`). Значительные дополнения оформляй отдельной Sub-issue.
- Счётчики `fix` и `Upd` **независимы** в пределах базовой версии. Новый Sub-issue начинается без суффиксов; число коммитов, PR и Actions runs на версию не влияет.
- **Уточнение пользователя от 2026-11-01:** версирование касается готовых билдов. После падения GitHub Actions исправлять причину и повторять сборку в рамках текущей версии, без увеличения `fix`/`Upd` из-за неудачного запуска. Следующий номер назначать следующему готовому билду; ранее выпущенные билды задним числом не переименовывать.
- Для отдельных компонентов экосистемы допускаются **независимые последовательности версий**: новая Issue MR Live сама по себе не повышает версию MR Studio DAW.
- **Одна версия на весь запуск сборки:** отображаемое имя конкретного GitHub Actions run (не номер запуска `#NNN`), версия приложения/пакета и имена **всех** публикуемых артефактов этого run (runtime ZIP, symbols/PDB, diagnostics/test results и других) должны содержать **одну и ту же точную версию соответствующего компонента**, включая суффиксы `-fixN` или `-UpdN`. Пример: `MR Live 0.8.12-fix1` в названии run и `MR-Live-0.8.12-fix1-...` во всех его артефактах. SHA и порядковый номер Actions дополняют идентификацию, но **не заменяют версию**.
- **Синхронизация версии в CI:** при подготовке сборки использовать единый источник версии для имени run, имён артефактов и package manifest; не оставлять устаревшую версию в workflow после `fix`/`Upd`. Для совместной сборки MR Studio/MR Live указывать версию каждого компонента явно и не подменять одну другой. Перед публикацией проверять совпадение; несоответствие исправить до выпуска артефактов, без переименования ранее принятых версий.
- **Единая версия в онлайне и локально:** версия из `apps/studio-desktop/include/mrs/version.hpp` должна совпадать в баннере приложения, `run-name` Actions, именах всех артефактов и имени каталога/ZIP пакета. Локальный прогон собранного артефакта использует ту же версию.
- Номер GitHub Issue (`#302` и т. п.) **не равен** номеру версии. Указывай версию этапа в Issue и отчёте, не переименовывай принятые версии задним числом без согласования.
- Успешная сборка не означает пользовательскую приёмку версии. Не закрывай Issue и не делай merge только из-за PASS CI.

## Старт и экономия токенов

1. Если **назначен Issue**, прочитай его критерии и **нужные фрагменты** связанных документов. Если Issue не назначен, выполняй конкретный запрос пользователя; не требуй создания Issue ради разовой проверки или правки. Не читай файлы только из-за наличия ссылок.
2. Перед изменением файлов: `git status --short`, ветка, HEAD. Сохраняй чужие/незакоммиченные изменения; не делай reset, stash, branch switch без согласования.
3. Используй поиск по классу, функции, номеру Issue и затем чтение **нужного диапазона** кода/документа. Не открывай полностью большие файлы, если достаточно раздела. Не перечитывай неизменённое в одном рабочем контексте.
4. **Не загружай по умолчанию** целиком `docs/PROJECT_CONTEXT.md`, `docs/LOCAL_BUILD_POLICY.md`, `docs/ROADMAP.md`, все Issues, весь `docs/` или все skills. Статус — из назначенного Issue, если он есть; контекст/политику находи поиском по теме. Для рисковых изменений обязательно читай релевантные правила безопасности.
5. `.agents/skills/`: открывай **только применимые SKILL.md**, а не всю папку. Для GUI/иконок/SVG — `mr-unified-gui/SKILL.md` + нужный раздел `docs/MR_UNIFIED_DESIGN_SYSTEM.md` (если skill отсутствует в checkout, сверяй с GitHub). Для RT/аудиографа — `mr-realtime-audio-safety` и релевантные разделы `docs/ENGINE_PERFORMANCE_PLAN.md`, `docs/PROCESSING_RELIABILITY.md`; для сборки — `.agents/skills/mr-studio-build-test/SKILL.md` и `docs/CLOUD_DEVELOPMENT.md` (действующий онлайн-процесс). `docs/LOCAL_BUILD_POLICY.md` — историческая справка.
6. Выполняй **только порученный этап**. Следующую задачу не начинай автоматически. Не требуй повторного разрешения на уже согласованную работу.

**Алгоритм:** `запрос/назначенный Issue → нужная спецификация и код → проверки по типу изменения → отчёт`.

## Архитектура и безопасность

- MR Studio и MR Live — Windows/JUCE/C++/ASIO приложения на общем коде Core. **MR Live — отдельное приложение**, запускаемое с Home MR Studio, со своим show-документом `.mrlive` и workflow по принятому онлайн-редактору. Переходов в Studio и прямого открытия Studio-песни через Live item нет. Studio → Live как Playback — отдельная будущая функция экспорта. Engine/ASIO/Transport/Project Model/GraphStore/MIDI/plugin host переиспользуются; второй backend не создавать. Это прямое уточнение пользователя от 2026-10-25; старые формулировки workspace handoff ему не соответствуют. См. `docs/MR_LIVE_NATIVE_INTEGRATION.md`.
- Изменения через принятые Commands/Model; сохраняй Undo/Redo, project persistence, plugin/editor lifetime, PDC, transport и raw recording. Миграции и новый формат состояния — только по обоснованной необходимости.
- **Audio callback:** никаких новых alloc/free, mutex/locks, disk/network I/O, UI calls. IR/NAM decode, подготовка эффектов, пересборка графа — вне callback; безопасный lifecycle worker/DSP и переключение. Не допускай двойного аудиотракта.
- **Studio mixing ≠ Live/recording:** 128 сэмплов не обязательны для всех студийных эффектов. RT производительность подтверждай callback/xrun измерениями, не одним процентом CPU.
- **GUI всей MR Studio (DAW/Live/все native plugins):** пользователь утвердил единый визуальный стиль `docs/MR_UNIFIED_DESIGN_SYSTEM.md` (dark blue-graphite, flat, тонкая светлая SVG-контурная графика) и skill `.agents/skills/mr-unified-gui/SKILL.md`. Реализуй только порученный GUI-объём с опорой на #189 MR UI Kit. До отдельной приёмки этапа действующая `ui::Theme` и ранее принятые экраны/цвета остаются as-built; не перекрашивай всё сразу, не меняй DSP и сторонние VST3 GUI.

## Правило воспроизводящего теста (Regression-first)

Для каждого багфикса применяется принцип **RED → GREEN**.

1. **RED:** до изменения кода создать тест, воспроизводящий ошибку из Issue, либо использовать существующий тест, который её выявляет.
2. Запустить тест на неисправленном коде и подтвердить, что он падает **именно из-за исследуемой ошибки**, а не из-за проблем окружения.
3. Только после подтверждения RED вносить исправление.
4. **GREEN:** повторно выполнить тот же тест и подтвердить успешное прохождение.
5. Сохранить регрессионный тест для предотвращения повторного появления ошибки.

### Защита тестов

- Запрещается удалять, отключать, комментировать или ослаблять падающие тесты ради успешного CI.
- Запрещается изменять существующие ассерты ради соответствия ошибочному поведению реализации.
- Корректировка тестов допускается при согласованном изменении требований либо при доказанной ошибке самого теста. Причину необходимо отдельно указать в PR.
- Успешная сборка без воспроизводящего теста не является достаточным доказательством исправления.

### Исключения для MR Studio / MR Live

Если автоматизированное воспроизведение объективно невозможно или непропорционально сложно (ASIO, аппаратные устройства, GUI, real-time audio):

- До исправления документировать точные шаги воспроизведения и наблюдаемый результат.
- По возможности добавить адресный автоматизированный тест для проверяемой части проблемы.
- После исправления выполнить повторную проверку теми же шагами.
- Если необходима проверка на оборудовании пользователя, отмечать её как **NOT TESTED** до пользовательской приёмки.
- Не объявлять ошибку полностью устранённой без соответствующего подтверждения.

### Отчёт Codex

Для каждого багфикса указывать:

- **RED:** тест, команда и причина исходного падения.
- **GREEN:** результат теста после исправления.
- **REGRESSION:** результаты необходимых смежных проверок.
- **NOT TESTED:** проверки, которые невозможно выполнить в текущем окружении.

Не запускать полную сборку или весь набор тестов, если для подтверждения исправления достаточно адресных проверок.

### Проверка перед завершением этапа

Перед отчётом о завершении задачи проверить:

- Новые и изменённые тесты, в том числе тест воспроизведения бага, прошли. Если автоматический репро-тест неприменим, зафиксировать результаты согласованной ручной проверки и оставшиеся ограничения.
- Целевой профиль CI для изменённого компонента прошёл. **Полный CI/CTest не обязателен для каждой правки**: выполнять его для согласованной интеграционной/релизной проверки либо при обоснованном риске, согласно действующей политике сборок. Docs-only и чисто визуальные изменения сохраняют утверждённые исключения.
- Diff не содержит несогласованных изменений вне области Issue.
- Если создаётся PR, в его описании указаны: **что изменилось, почему и как воспроизвести баг до исправления** (для задач без бага — как проверить результат). Указать фактически проведённые проверки и ограничения.

Если обязательная для данного этапа проверка завершилась с FAIL или NOT TESTED, **не объявлять этап полностью проверенным**; явно указать блокер или ожидание пользовательской приёмки.

### Стиль и границы реализации

- Соблюдать существующие конвенции и архитектурные паттерны проекта. При конфликте личного предпочтения исполнителя с принятым проектным решением приоритет у проекта и актуальных требований.
- Не добавлять новые зависимости без согласования. Если зависимость действительно необходима, сначала обосновать её в соответствующей Issue; не вводить самостоятельно.
- Обработку ошибок и логирование выполнять по действующим паттернам соответствующего компонента, предварительно проверив соседний код; не создавать параллельные механизмы без необходимости.
- Не вводить абстракции и расширения «на будущее» без требований текущей Issue. Реализовать минимальный достаточный объём, сохранив совместимость общих компонентов.

### Отчётность по исправлению

- По завершении работы оставить комментарий **в конкретной Issue/Sub-issue**: что сделано, какие тесты добавлены/изменены, их RED/GREEN-результаты, что **не сделано или не проверено**, а также ссылки на commit/PR/CI при наличии.
- Не писать «исправлено» для бага, пока не выполнена проверка на исходном репро-кейсе: автоматическая или, в обоснованном исключении, повторная ручная. Успешная сборка сама по себе не заменяет эту проверку.
- Разделять **код реализован**, **проверки PASS** и **пользовательская приёмка**. Не закрывать Issue и не выполнять merge без требуемой приёмки.

### Работа с CI

- **Порядок, запуск, зависимости и предварительные проверки CI определяются только актуальными `.github/workflows/` и используемыми ими скриптами `tools/ci/`.** Не обходить обязательные gates, не объявлять PASS непроверенный профиль. Merge в `main` — после пользовательской приёмки.
- **Правило поведения агента, а не YAML:** частоту ручного опроса GitHub Actions выбирать по ситуации, учитывая длительность проверки и доступные инструменты. Предпочитать уведомление о завершении без опроса; не делать параллельные одинаковые запросы.
- При FAIL читать конкретные шаги/логи и проводить адресную диагностику до повторного запуска; не повторять заведомо неудачный цикл без новой гипотезы.

### Действия при блокере

- После **трёх безрезультатных попыток исправления одной и той же ошибки** остановить изменения «наугад» и повторные сборки без новой гипотезы.
- Зафиксировать в Issue наблюдения, проверенные гипотезы, результаты тестов/логов, неудачные подходы и следующий диагностический шаг; отметить, что остаётся непроверенным.
- Продолжать только с обоснованной новой гипотезой или дополнительными данными. Если причина остаётся неизвестной и без пользовательского ввода двигаться нельзя, явно сообщить о блокере; не объявлять фикс выполненным.

- **Уточнение пользователя для текущей #29:** минимальные адресные проверки нового поведения; широкий регрессионный прогон — в конце родительской задачи. - **Уточнение пользователя от 2026-10-31 для продолжающейся MR Live / #31:** «Запускай сборки сам, спрашивай только про merge в main». Необходимые адресные Windows Live-only сборки, исправления CI и повторные запуски выполнять самостоятельно, без повторного запроса. Это уточнение заменяет прежнее требование отдельной команды на каждый запуск для текущей работы. Merge в `main` требует отдельного явного одобрения пользователя; CI не заменяет пользовательскую/аппаратную приёмку. Выбирать объём проверок по фактическому риску, не запускать полный CTest автоматически.

- **Прямое указание пользователя от 2026-10-26:** исправления интерфейса включать в продолжающуюся разработку; формулировка «учесть в следующем билде» сама по себе не является командой собрать отдельный билд. Новую сборку запускать только по прямой команде пользователя. Не инициировать её косвенно через push/PR, если workflow автоматически собирает Windows. Уже запущенную 0.8.3 пользователь разрешил завершить. Уточнение пользователя для #29: функциональная интеграция реального Playback разрешает необходимые сборки и профильные проверки; ограничение относится к тяжёлому автоматическому прогону из-за незначительных изменений интерфейса.

- **Визуальное исключение пользователя от 2026-10-18:** иконки, цвета, фон, оттенки и оформление без изменений поведения, hit areas, layout, bindings, модели, Undo/persistence, DSP, зависимостей и конфигурации сборки требуют только проверки diff и корректности исходников/ресурсов. Автотесты, GUI smoke, скриншоты, preview и DPI-прогоны не нужны; визуально проверяет пользователь. Даже при изменении C++/встроенных ресурсов адресная сборка GUI нужна лишь когда запрошено обновлённое приложение; при «без сборки» сообщи, что результат появится после следующей сборки. Тесты — по отдельному запросу или при выходе за этот объём. Правило отменяет прежние требования V1/L1 к preview/smoke/тестам в skills и документации; не заявляй непроведённую проверку интерфейса.
- **Только документация:** проверь diff и согласованность изменённых правил/ссылок; сборка и тесты приложения не нужны.
- **Код вне визуального исключения:** сборка поддержанного профиля CI + затронутые тесты по фактическому риску. Для аудиографа/host — релевантные RT/PDC/regressions/GUI smoke. При изменении геометрии, поведения, общих зависимостей или сбое расширь проверки по фактическому риску; это само по себе не требует повторного разрешения на порученную работу.
- **Полный CTest (L4):** только для отдельно согласованного релизного/интеграционного кандидата либо при обоснованной необходимости; укажи основание. Визуальная приёмка косметической правки сама по себе не повод для L4. Не запускай массовые DPI-проверки, упаковку и смену ярлыка без необходимости в рамках запроса. Не повторяй специальные TH-U/Nuro проверки без соответствующей проблемы; синтетические VST3 тесты сохраняются.
- Исключения выше определяют проверки, запускаемые агентом; автоматические CI workflows могут выполнять больше. Не меняй workflows ради обхода проверок без отдельной задачи.
- Отмечай реальные PASS/FAIL/**NOT TESTED**. CI не подтверждает физическую ASIO производительность, слух или физический DPI.
