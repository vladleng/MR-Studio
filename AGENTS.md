# MR Studio / MR Live — проектные правила

## Активный режим разработки

Development mode: CLOUD

Режим задаёт пользователь; для возврата к локальной разработке достаточно изменить значение на `LOCAL` и синхронизировать задачи и Git. Не определяй режим по наличию DSH, локальных скриптов или GitHub. При несовпадении среды с активным режимом сообщи об ограничении, не переключайся сам. Этот файл определяет проектные правила в обоих режимах; противоречащие ему исторические инструкции и локальные Skills не переопределяют активный режим. Не загружай все Skills или `docs/` при старте задачи.

## Источники истины и ход работы

- **CLOUD:** GitHub `vladleng/MR-Studio`, актуальный `main` и тематическая ветка — источники исходников; GitHub Issues/Sub-issues — требования, состояние и приёмка; Codex Cloud — среда разработки; GitHub Actions — удалённые проверки и сборки. Локальный Windows-ПК — пользовательская и аппаратная приёмка. Не требуй доступа к DSH Task Manager. Адресная справка: `docs/CLOUD_DEVELOPMENT.md`.
- **LOCAL:** разработка, исходники, Git, сборки и артефакты — локальный Windows checkout; DSH Task Manager, проект «MR Studio» — требования, состояние и приёмка. GitHub Issues/PR/Actions и опубликованный `main` не являются текущим трекером; не подменяй локальный код облачной версией. Адресная справка: `docs/LOCAL_BUILD_POLICY.md`.
- При переходе между режимами сверяй HEAD/версии и перенос незавершённых задач в активный трекер; не считай задачи автоматически принятыми, не дублируй записи и не веди два активных трекера.
- Рабочая последовательность: **задача → адресное исследование кода и тестов → реализация в согласованном объёме → проверки по риску → краткий результат**. Документацию открывай только ради конкретного контракта, который нельзя надёжно восстановить из кода, тестов и задачи.
- Вопросы и аудит — только чтение. Изменяй код, задачи и документы лишь в рамках порученной работы. Новые зависимости, изменение формата проекта, внешних API или расширение scope согласовывай, если они не входят в задачу.

## Git, задачи и приёмка

- Перед изменением кода проверь текущую ветку, HEAD, `git status --short` и существующий diff. Сохраняй чужие и незакоммиченные правки; не выполняй `reset`, `stash` или смену ветки без согласования.
- **CLOUD:** для порученной реализации используй тематическую ветку от актуального `main`, коммиты, push в эту ветку и PR для проверки/интеграции. Не пушь напрямую в `main`. Перед push проверь исходящий diff. Профильные Actions, необходимые для порученных проверок и подготовки кандидата, разрешены в scope задачи; их триггеры, зависимости и gates определяет CI, а не этот файл. Не публикуй GitHub Release без отдельного поручения. Merge в `main` и закрытие Issue — только после явной пользовательской приёмки и согласования merge/закрытия. В Issue/Sub-issue фиксируй существенные результаты, версию, PR, проверки, артефакты и блокеры; не закрывай родительскую задачу автоматически.
- **LOCAL:** локальные коммиты по законченным изменениям допустимы без отдельного разрешения. Merge и push — только после явной приёмки и отдельного согласования; перед push проверь исходящие коммиты. Если код уже в целевой ветке, merge не требуется. Не создавай PR для обычной локальной работы. Actions, публикация релиза и отправка материалов — только по прямому запросу. В DSH Task Manager фиксируй существенные результаты и блокеры; готовый результат — **Wait**, **Done** — только после явной пользовательской приёмки; родительскую задачу автоматически не закрывай.
- В обоих режимах не создавай параллельные журналы `PLAN.md`/`PROGRESS.md`.
- Версионирование сборок Studio и Live независимое. Для назначения версий, `-fixN`/`-UpdN`, имени приложения и пакета адресно смотри `docs/VERSIONING.md`; не меняй уже выпущенные версии задним числом.

## Неизменяемые технические границы

- **MR Studio** — DAW; **MR Live** — отдельное приложение JUCE/Windows с `.mrlive`, запускаемое с Home. Используют общий Core/Engine/ASIO/Transport/Model/GraphStore/MIDI/plugin host. Не создавай второй backend или несанкционированные переходы между форматами Studio/Live. Изменение Shared Core оценивай для обоих приложений.
- Сохраняй существующие контракты Commands/Model, Undo/Redo, persistence, MIDI и automation, PDC, transport, recording, жизненный цикл plugin processor/editor, идентификаторы параметров и совместимость пресетов. Их намеренное изменение допускается только в scope задачи с адресной проверкой зависимостей.
- **Real-time audio:** в callback запрещены новые allocation/free, locks/mutex, disk/network I/O и UI-вызовы. Декодирование и тяжёлая подготовка — вне callback; переключения и жизненный цикл потокобезопасны. Производительность RT подтверждай callback/xrun измерениями, а не только CPU%.
- **ARA2:** Studio по умолчанию ON; Live standalone без ARA2 и без ARA SDK/scanner в пакете. Studio-only сборка — с `MRS_BUILD_LIVE=OFF`, если этого требует фактическая конфигурация. Не запускай проверки Live ради Studio-only изменений без причин, но проверяй затронутый общий Core.
- **GUI:** код существующих контролов и компонентов — исходная реализация, а не запрет на развитие дизайна. При багфиксе не меняй соседние элементы без необходимости; при порученном улучшении/редизайне разрешены новые геометрия, композиция, палитра и общие компоненты в пределах scope. Сохраняй bindings, состояния и поведение; не меняй DSP или сторонние VST3 GUI ради оформления.
- Не публикуй SDK, секреты, проприетарные плагины, пользовательские проекты, WAV/NAM и защищённые материалы. Не удаляй существующие сборки, кэши и настройки без отдельного поручения. Исходники и история Git требуют резервного копирования вне локального ПК.

## Десять доступных Skills — только по потребности

Все находятся в `.agents/skills/`. **Наличие Skill не делает его обязательным**: сначала оцени задачу, читай только применимый `SKILL.md` и нужные references. Не запускай цепочки других Skills без конкретной причины.

| Skill | Когда нужен |
| --- | --- |
| `dsh-task-manager-workflow` | Только LOCAL: работа с задачами, подзадачами, статусами, чек-поинтами или приёмкой DSH. Не нужен для CLOUD или обычного вопроса без записи в журнал. |
| `mr-github-workflow` | Только CLOUD: назначенные GitHub Issues/Sub-issues, тематические ветки, PR, CI evidence, отчётность и приёмка. Не нужен для LOCAL или обычного вопроса без записи в журнал. |
| `mr-studio-build-test` | Выбор/выполнение тестов и сборок в активном режиме, диагностика FAIL, подготовка пакета. |
| `mr-realtime-audio-safety` | Изменение RT callback, аудиографа, маршрутизации, transport timing, host, recording или межпоточного состояния аудио. |
| `mr-unified-gui` | Нетривиальная разработка/переработка GUI, иконок, SVG, общих контролов и визуальная оценка. Не обязателен для простой локальной правки. |
| `mr-studio-ui-design-system` | Только когда нужны дополнительные технические детали JUCE, LookAndFeel, layout, focus, DPI или окон; не открывать автоматически вместе с `mr-unified-gui`. |
| `ds-design` | Опционально для поиска нового визуального направления по явному дизайнерскому запросу; не применять автоматически к нативному JUCE GUI. |
| `ds-blast-radius` | Существенный риск влияния на Shared Core, Studio/Live, API, форматы, плагины или соседние подсистемы. |
| `ds-review-loop` | Адресное ревью существенного/рискованного diff; не запускать рутинно и не требовать субагента по умолчанию. |
| `ds-unstick` | Та же неисправность остаётся после двух осмысленных попыток исправления; не использовать после первого FAIL. |

`docs/START_HERE.md`, `docs/README.md`, `docs/LOCAL_BUILD_POLICY.md`, `docs/MR_LIVE_NATIVE_INTEGRATION.md` и другие документы — **справочники по необходимости**, а не обязательный список чтения. Не следуй устаревшим handoff, roadmap и инструкциям другого режима вопреки текущей задаче, коду и активному режиму.

## Самостоятельные проверки и диагностика

- Агент **сам выбирает минимально достаточный уровень L0–L4** по риску изменения, а не по числу файлов. Используй действующие CMake/scripts/targets и, в CLOUD, соответствующие `.github/workflows/`; подробности уровней — в `mr-studio-build-test`. Адресные проверки в рамках порученной реализации не требуют нового согласования. В CLOUD проверяй фактические workflows, профили и SHA; отсутствующий Windows Release или обязательный gate — блокер выпуска, не заменяй его Linux PASS и не восстанавливай CI без поручения. Полный L4 — для согласованной интеграции/релиза либо обоснованного риска; укажи причину.
- Для багфикса сначала воспроизведи проблему (**RED**) подходящим тестом либо, если тест непропорционален/невозможен, точными шагами. После исправления проверь тот же сценарий (**GREEN**). Не отключай и не ослабляй падающие тесты ради PASS.
- Для GUI-редизайна по возможности проверь затронутое поведение и реальный визуальный результат. При недоступном интерфейсе укажи **NOT TESTED**, не выдавай проверку кода за проверку внешнего вида.
- При повторном FAIL изучай причину и проверяй новую гипотезу до дорогой сборки. После **двух безрезультатных попыток одной ошибки** применяй `ds-unstick`; после **трёх** прекращай правки наугад, фиксируй факты и блокер. Если сложность именно аналитическая, можешь **предложить** повысить уровень рассуждений или модель, объяснив стоимость; **не переключай платную модель/провайдера без разрешения**.
- Перед завершением проверь scope diff и фактические результаты проверок. Различай **реализовано / PASS / NOT TESTED / принято пользователем**. В отчёте кратко укажи результат, нужные команды и конфигурацию, ограничения, ветку/HEAD и коммит при наличии.

## Документация

- Источник истины для реализованного поведения — код и тесты. Документ сохраняй или создавай только для **уникального долгосрочного контракта**, не выводимого надёжно из реализации; техническое решение для текущей задачи, этапы и приёмка живут в активном трекере (GitHub Issues или DSH Task Manager) и Git.
- Перед удалением старого документа проверь уникальные требования и входящие ссылки. Не превращай обновление реализации в обязательное переписывание архитектурных обзоров. Правки проектных правил/Skills делай отдельным docs-only коммитом, если поручена фиксация изменений.
