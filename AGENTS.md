# MR Studio — правила Codex (Issue-first)

Этот файл содержит **только постоянные правила**. Не загружай всю документацию проекта ради одной задачи.

## Среда разработки и публикация

GitHub — единый источник кода, документации и Issues. Codex Cloud — основная среда разработки; checkout отражает текущую ветку и незавершённые изменения. GitHub Actions собирает Windows JUCE/VST3/ASIO; **ARA2 ON по умолчанию для MR Studio**, но **MR Live standalone всегда без ARA2** (адресный `checks=live`: ARA OFF, без ARA SDK/scanner в Live-артефакте; при совместной сборке Studio+Live ARA есть только в Studio). Для Studio ARA OFF допускается только как явно запрошенная диагностическая сборка; полный CTest — отдельно. См. #303 и `docs/MR_LIVE_NATIVE_INTEGRATION.md`. Локальный ПК служит преимущественно для пользовательской приёмки и аппаратных ASIO/MIDI/DPI/vendor тестов.

Source commits/push в тематической ветке разрешены в рамках порученной разработки. CI запускается согласно workflows; полный CTest только для явно выбранной интеграционной/релизной проверки или обоснованного риска. Merge в main — только после отдельной пользовательской приёмки. Нельзя объявлять физическую ASIO производительность по CI. SDK/секреты/проприетарные плагины/пользовательские проекты и принятые локальные сборки не публиковать и не менять. Действующий процесс: docs/CLOUD_DEVELOPMENT.md.

## Источники истины

- **GitHub `main`** — эталон `AGENTS.md`, тематических спецификаций и Issues (ТЗ, статусы, приёмка). `AGENTS.md` текущей ветки определяет работу Codex в этой задаче; main остаётся документальной базой, изменения правил согласовываются с пользовательским запросом. Проверяй расхождения **точечно**, не синхронизируй весь `docs/` перед каждой задачей.
- **Checkout задачи** — фактический код, незавершённые изменения, сборки и результаты тестов; он может опережать GitHub. Issue не доказывает, что код реализован; код/тесты не доказывают пользовательскую приёмку.
- При конфликте: **текущий запрос пользователя → актуальный Issue/подтверждённая приёмка → каноническая спецификация**. Старые roadmap, сводки и handoff — справка, не замена новых решений. Противоречия проверяй и сообщай, не исправляй догадками.
- Markdown-чеклисты не являются нативными GitHub Sub-issues; не заявляй проценты прогресса без проверки реальной иерархии.

## Правила версирования Issues и Sub-issues

Единая схема для соответствующей линии разработки: **`0.I.S`** (например, `0.8.8`).

- **Первая цифра** (`0`) — основной этап разработки; меняется только по отдельному согласованному решению.
- **Вторая цифра** (`I`) — номер этапа родительской Issue; увеличивается **только при старте следующей родительской Issue**, не при исправлениях, коммитах, PR или сборках. Пример: `0.8.0 → 0.9.0`.
- **Третья цифра** (`S`) — порядковый номер Sub-issue в текущей родительской Issue: `0.8.1`, `0.8.2`, …; при переходе к новой родительской Issue сбрасывается в `0`. Если Sub-issues нет, используется версия `0.8.0`.
- **Исправление ошибки** текущей версии — суффикс `-fix1`, `-fix2`, … (например, `0.8.8-fix1`). Ошибки и регрессии не увеличивают базовую версию.
- **Небольшое дополнение** в рамках той же Sub-issue — суффикс `-Upd1`, `-Upd2`, … (например, `0.8.8-Upd1`). Значительные дополнения оформляй отдельной Sub-issue.
- Счётчики `fix` и `Upd` **независимы** в пределах базовой версии. Новый Sub-issue начинается без суффиксов; число коммитов, PR и Actions runs на версию не влияет.
- Для отдельных компонентов экосистемы допускаются **независимые последовательности версий**: новая Issue MR Live сама по себе не повышает версию MR Studio DAW.
- **Одна версия на весь запуск сборки:** отображаемое имя конкретного GitHub Actions run (не номер запуска `#NNN`), версия приложения/пакета и имена **всех** публикуемых артефактов этого run (runtime ZIP, symbols/PDB, diagnostics/test results и других) должны содержать **одну и ту же точную версию соответствующего компонента**, включая суффиксы `-fixN` или `-UpdN`. Пример: `MR Live 0.8.12-fix1` в названии run и `MR-Live-0.8.12-fix1-...` во всех его артефактах. SHA и порядковый номер Actions дополняют идентификацию, но **не заменяют версию**.
- **Синхронизация версии в CI:** при подготовке сборки использовать единый источник версии для имени run, имён артефактов и package manifest; не оставлять устаревшую версию в workflow после `fix`/`Upd`. Для совместной сборки MR Studio/MR Live указывать версию каждого компонента явно и не подменять одну другой. Перед публикацией проверять совпадение; несоответствие исправить до выпуска артефактов, без переименования ранее принятых версий.
- Номер GitHub Issue (`#302` и т. п.) **не равен** номеру версии. Указывай версию этапа в Issue и отчёте, не переименовывай принятые версии задним числом без согласования.
- Успешная сборка не означает пользовательскую приёмку версии. Не закрывай Issue и не делай merge только из-за PASS CI.

## Старт и экономия токенов

1. Прочитай **назначенный Issue**, его критерии и **нужные фрагменты** связанных документов. Не читай подряд все связанные файлы только из-за наличия ссылок.
2. Перед изменением кода: `git status --short`, ветка, HEAD. Сохраняй чужие/незакоммиченные изменения; не делай reset, stash, branch switch без согласования.
3. Используй поиск по классу, функции, номеру Issue и затем чтение **нужного диапазона** кода/документа. Не открывай полностью большие файлы, если достаточно раздела. Не перечитывай неизменённое в одном рабочем контексте.
4. **Не загружай по умолчанию** целиком `docs/PROJECT_CONTEXT.md`, `docs/LOCAL_BUILD_POLICY.md`, `docs/ROADMAP.md`, все Issues, весь `docs/` или все skills. Статус — из актуального Issue; контекст/политику находи поиском по теме. Для рисковых изменений обязательно читай релевантные правила безопасности.
5. `.codex/skills/`: открывай **один нужный SKILL.md**, а не всю папку. Для всего GUI/иконок/SVG — `.codex/skills/mr-unified-gui/SKILL.md` + нужный раздел `docs/MR_UNIFIED_DESIGN_SYSTEM.md` (если skill отсутствует в локальном checkout, сверяй его с GitHub); не загружай все UI docs. Для RT/аудиографа — relevant `mr-realtime-audio-safety`, `docs/ENGINE_PERFORMANCE_PLAN.md`, `docs/PROCESSING_RELIABILITY.md`; для сборки — нужный раздел build policy.
6. Выполняй **только порученный этап**. Следующую задачу не начинай автоматически. Не требуй повторного разрешения на уже согласованную работу.

**Алгоритм:** `Issue → точечная спецификация → нужный код → профильные проверки/CI → отчёт в Issue`.

## Каноническая библиотека GUI assets

- Локальная библиотека **MR UDS SVG Kit**: `assets/ui/mr-uds/` (svg/controls/, svg/icons/, svg/rig/, svg/reverb/, previews/, tokens/, build_kit.py, manifest.json, README.md). Существующий `assets/ui/icons/transport/` не переносить автоматически.
- Перед созданием новых GUI-иконок проверяй `assets/ui/mr-uds/manifest.json` и SVG по относительным путям `svg/...`, затем `docs/MR_UNIFIED_DESIGN_SYSTEM.md` и `.codex/skills/mr-unified-gui/SKILL.md`; дубли не создавать.
- `build_kit.py` — вспомогательный генератор: **не запускать автоматически** до проверки путей, перезаписываемых файлов и зависимостей. GUI assets и generator редактировать в checkout задачи и проверять по текущей политике исходников.
- Не путай локальную asset library с GitHub: папка может отсутствовать в удалённом репозитории; перед использованием проверить существование в checkout.

## Архитектура и безопасность

- MR Studio и MR Live — Windows/JUCE/C++/ASIO приложения на общем коде Core. **MR Live — отдельное приложение**, запускаемое с Home MR Studio, со своим show-документом `.mrlive` и workflow по принятому онлайн-редактору. Переходов в Studio и прямого открытия Studio-песни через Live item нет. Studio → Live как Playback — отдельная будущая функция экспорта. Engine/ASIO/Transport/Project Model/GraphStore/MIDI/plugin host переиспользуются; второй backend не создавать. Это прямое уточнение пользователя от 2026-10-25; старые формулировки workspace handoff ему не соответствуют. См. `docs/MR_LIVE_NATIVE_INTEGRATION.md`.
- Изменения через принятые Commands/Model; сохраняй Undo/Redo, project persistence, plugin/editor lifetime, PDC, transport и raw recording. Миграции и новый формат состояния — только по обоснованной необходимости.
- **Audio callback:** никаких новых alloc/free, mutex/locks, disk/network I/O, UI calls. IR/NAM decode, подготовка эффектов, пересборка графа — вне callback; безопасный lifecycle worker/DSP и переключение. Не допускай двойного аудиотракта.
- **Studio mixing ≠ Live/recording:** 128 сэмплов не обязательны для всех студийных эффектов. RT производительность подтверждай callback/xrun измерениями, не одним процентом CPU.
- **GUI всей MR Studio (DAW/Live/все native plugins):** пользователь утвердил единый визуальный стиль `docs/MR_UNIFIED_DESIGN_SYSTEM.md` (dark blue-graphite, flat, тонкая светлая SVG-контурная графика) и skill `.codex/skills/mr-unified-gui/SKILL.md`. Реализуй в рамках назначенного GUI Issue с опорой на #189 MR UI Kit. До отдельной приёмки этапа действующая `ui::Theme` и ранее принятые экраны/цвета остаются as-built; не перекрашивай всё сразу, не меняй DSP и сторонние VST3 GUI.

## Разработка и публикация

- **Уточнение пользователя для текущей #29:** минимальные адресные проверки нового поведения; широкий регрессионный прогон — в конце родительской задачи. Не запускать автоматически существующий Windows workflow со всем профилем ради отдельного исправления плейхэда. Для явно согласованного адресного запуска есть `[ci live]` в заголовке source commit или manual `checks=live`: только GUI target и два Live smoke; остальные профили/интеграция сохраняют прежний scope.

- **Прямое указание пользователя от 2026-10-26:** исправления интерфейса включать в продолжающуюся разработку; формулировка «учесть в следующем билде» сама по себе не является командой собрать отдельный билд. Новую сборку запускать только по прямой команде пользователя. Не инициировать её косвенно через push/PR, если workflow автоматически собирает Windows. Уже запущенную 0.8.3 пользователь разрешил завершить. Уточнение пользователя для #29: функциональная интеграция реального Playback разрешает необходимые сборки и профильные проверки; ограничение относится к тяжёлому автоматическому прогону из-за незначительных изменений интерфейса.

- **Правило пользователя от 2026-10-18 — чисто визуальные правки:** замена иконок, цветов, фона, оттенков и подобного оформления без изменения поведения, hit areas, layout, bindings, модели, Undo/persistence, DSP, зависимостей или конфигурации сборки не требует автоматических тестов, GUI smoke, скриншотов, превью или DPI-прогонов. Визуальную проверку выполняет пользователь. Достаточно проверить diff и корректность изменённых исходников/ресурсов; не заявлять проверку интерфейса, если её не было. Если C++ или встроенный ресурс требует перекомпиляции для отображения, это не отменяет исключение из тестов: нужна лишь адресная инкрементальная сборка GUI, когда получение обновлённого приложения входит в запрос. При явном «без сборки» оставить изменение в исходниках и сообщить, что оно появится после следующей сборки. Тесты — только по отдельному запросу или при фактическом выходе за указанный визуальный объём. Это правило имеет приоритет над прежними требованиями V1/L1 о preview, visual smoke и тестах в этом файле, skills и документации.
- Source, commits и инструменты разработки находятся в GitHub/Codex Cloud. Windows builds/tests/packages создаются Actions, artifacts содержат runtime отдельно от PDB/логов. Не изменяй пользовательские проекты/настройки/WAV/NAM; fixtures создавай в отдельной папке.
- Публикуй исходники и необходимые docs/skills/assets в тематической ветке. Обновляй конкретный Issue по содержательным результатам; не дублируй хронологию в docs. Merge без отдельной приёмки запрещён.
- Код: сборка поддержанного профиля CI + затронутые тесты по фактическому риску; аудиограф/host — RT/PDC/regressions/GUI smoke. **Полный CTest (L4) — только для отдельно согласованного релизного/интеграционного кандидата либо при обоснованной необходимости, не после каждой мелкой правки. Визуальная приёмка косметического изменения (V1: фон, цвет, оттенок SVG, толщина контура без изменения геометрии и поведения) сама по себе НЕ делает правку кандидатом L4.** Для чисто косметического V1 действует исключение пользователя выше: diff/исходники, без обязательных smoke/preview/DPI; C++ требует только адресной сборки, если нужен обновлённый EXE. Не запускай автоматически полный CTest, массовые DPI-проверки, упаковку и смену ярлыка. Эскалируй при изменении геометрии, поведения, затронутых общих зависимостей, сбое или прямом запросе. **Docs-only изменения не требуют сборки.** Отмечай реальные PASS/FAIL/**NOT TESTED** (особенно ASIO, слух, физический DPI). Не повторяй специальные TH-U/Nuro проверки без соответствующей проблемы; синтетические VST3 тесты сохраняются.
- Сторонние защищённые WAV/NAM/изображения не добавляй в репозиторий или пакеты без прав и разрешения.

## Приёмка и передача

- Обновляй **конкретный Issue**: что сделано, локальный commit/пакет, тесты, ограничения, что ждёт проверки. Закрывай лишь после пользовательской приёмки **этого объёма**, не всего parent по умолчанию.
- Тематические docs изменяй **при изменении контракта**, без дублирования отчётов. `PROJECT_CONTEXT.md` — **короткий указатель на актуальное**, при необходимости; не обязательный накопительный журнал и не обязательное чтение целиком.
- Отвечай по-русски и кратко: результат, проверки, ограничения, следующий шаг. Не вставляй в чат большие логи.
