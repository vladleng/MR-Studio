# Облачная разработка и Windows CI/CD

Применяется в режиме **CLOUD**, выбранном в [AGENTS.md](../AGENTS.md). В режиме LOCAL используй [локальный процесс](LOCAL_BUILD_POLICY.md); этот документ не даёт самостоятельного разрешения на Actions, push или публикацию. Историческая миграция: [#241](https://github.com/vladleng/MR-Studio/issues/241) (закрыта 2026-10-20).

**Проверяй доступность CI:** Windows Studio Release определён в `.github/workflows/audio-engine.yml`; перед запуском проверяй его регистрацию и актуальный профиль, версии из `apps/studio-desktop/include/mrs/version.hpp` и обязательные evidence gates. Наличие файла не подтверждает успешную сборку. Не объявляй Windows-пакет готовым на основании GUI Compile.

## Источники и среда
GitHub main — основа исходников и документации. Задания, scope, решения и приёмка задаются в текущем чате; номер Issue не требуется. Issues используются только по отдельному поручению или как адресный исторический справочник. Codex Cloud или агент с доступными инструментами GitHub работает в тематической ветке с текущим AGENTS.md и проектными skills. Локальная Windows-машина нужна преимущественно для пользовательской приёмки, физических ASIO/MIDI/DPI и licensed vendor проверок. Локальные инструкции в LOCAL_BUILD_POLICY/LOCAL_WORKSPACE действуют только в режиме LOCAL и не запрещают разрешённый облачный CI/source push.

По [актуальному руководству Codex Cloud](https://learn.chatgpt.com/docs/environments/cloud-environments), создать среду через Work in > Cloud > Create environment либо Settings > Codex Cloud > Environments, подключить vladleng/MR-Studio, проверить подготовку и опубликовать среду (Publish). Для изменения подготовленной среды нужен Republish; существующие задачи сохраняют своё состояние. Legacy Cloud — отдельный процесс для прежних интеграций, не основная инструкция для новых задач.

В диалоге подготовки указать Linux, CMake>=3.22, C++20 compiler и Git; предложить `bash tools/ci/Setup-CodexCloud.sh` как команду Install script из репозитория. Скрипт конфигурирует Core без закрытых SDK и полного CTest. На ветке задачи после обновления исходников повторить configure при изменении CMake. Для проверки среды собрать профильные Core targets и выполнить соответствующие CTest, затем сохранить отчёт подготовки. Windows GUI проверяется отдельно Actions. Наличие скрипта не доказывает публикацию среды или успешный запуск задачи Codex Cloud; это пока NOT TESTED. Доступ к GitHub и сети настраивается средствами среды, секреты не помещать в скрипт.

## SDK и кэш
`tools/ci/sdk-lock.json` закрепляет JUCE9.0.3, VST3 SDK, PortAudio и ARA SDK2.3.0 immutable commits. ARA2 входит в обычную Windows-сборку по умолчанию; ручной ARA-OFF — только для диагностики. Submodule commits определяются gitlinks закреплённого родителя. Actions также закреплены SHA.
`Prepare-Sdks.ps1` получает SDK только из указанных официальных origins, проверяет commit/dirty state/submodules. Public-source cache keyed lock hash + ARA profile; без restore-prefix fallback. Fork PR не записывает общий cache. ASIO ZIP скачивается с официального HTTPS endpoint и проверяется существующим SHA256; изменение архива — ошибка с явным review версии/лицензии, не автоматическая смена pin.
ASIO ZIP и извлечённые ASIO sources находятся вне кэшируемого `build/sdk`, не попадают в Git/artifacts. В package включается license notice, не SDK. Не вносить токены/плагины/пользовательские WAV/NAM в caches. Публичный source cache — оптимизация, а не доказательство корректности: pin checks обязательны на hit.

## Архитектура CI

**Исполняемый источник истины — актуальные `.github/workflows/*.yml` и скрипты `tools/ci/` текущей ветки.** Именно там находятся триггеры, входные профили, зависимости jobs, условия выпуска артефактов и отмены устаревших запусков. Не дублировать эти параметры в `AGENTS.md`, Skill и данном документе.

Проверки делятся на быстрые Core-контракты без Windows GUI/ASIO/VST3/ARA, профильные компонентные контракты и Windows-интеграцию/пакет пользовательской приёмки. Успех Linux Core не доказывает Windows-совместимость, ASIO, реальный GUI или качество звучания; соответствующие проверки остаются в профильном Windows-контуре.

Кандидат Windows Studio Release запускается вручную через workflow_dispatch либо явным изменением заголовка PR из этого же репозитория в main: префикс `[candidate:studio]`, `[candidate:live]` или `[candidate:studio-live]`. Добавление префикса выбирает SHA head на момент события; обычный commit, правка описания PR или сохранённый префикс не запрашивают новый кандидат. Для повторного запроса сначала убрать префикс, затем добавить его заново на нужном SHA. Не использовать это как пользовательскую приёмку или разрешение merge. В автоматическом режиме план переиспользует успешные evidence exact-SHA, ожидает выполняющиеся проверки (до 30 минут), запускает только недостающие контуры через существующие reusable workflows и блокируется при явной ошибке. Ручной режим по-прежнему не запускает проверки сам.

Перед тяжёлой Windows job read-only preflight подтверждает фактический checkout SHA, профиль и хеш определения workflow/регистратора для каждого обязательного контура. Для уже существующих проверок нужен последний завершённый успешный запуск и непосроченный evidence artifact; для запущенных текущим кандидатом — успешная зависимость job и её evidence того же SHA. PR-проверки checkout-ят head SHA, а не синтетический merge. MP3-контракт обязателен для обычного Studio-кандидата, но не Live-only. Failure/cancelled/pending, отсутствующее или неподходящее evidence блокируют сборку. Переход ссылки на новый SHA требует свидетельств нового SHA.

Evidence хранится 14 дней; после истечения срока автоматический запрос кандидата планирует соответствующую проверку, ручной запуск Release требует предварительного повторного запуска проверки. Проверки старого формата без evidence не принимаются. `verify_ci_evidence.py` проверяет результаты, `verify_candidate_gate.py` определяет обязательные контуры профиля; `verify_release_gate.py` сохранён только для совместимости старых веток. Windows-сборка зависит от preflight. До сборки и упаковки сохраняется проверка актуальности ссылки. Повторная установка runtime внутри application job исключена; базовая GUI-компиляция без ARA/ASIO не заменяет проверки включённых вариантов в Windows Release.

Для текущего профиля выбирать проверку по реальному затронутому компоненту, не называть завершённой проверку, которая не выполнялась. Порядок действий агента при анализе ошибки и пользовательской приёмке описан в `.agents/skills/mr-studio-build-test/SKILL.md`, но **правила запуска исполняют действующие Actions**. При создании новой специализированной проверки нужно включить её в зависимости/gate на уровне CI, а не добавлять отдельное текстовое правило в каждый документ.

### ARA2 и совместимость

Studio использует ARA2 по принятому умолчанию, Live-only — без ARA2. Для диагностической Studio-сборки без ARA2 необходим явно выбранный профиль. Результаты plugin/render fixtures отмечаются по фактическим данным CI; тесты нельзя удалять ради PASS.

В CI одна и та же обработанная ARA render-fixture применяется для `ara_clip_model` и `ara_clip_processed`. Её штатный коэффициент при 120 BPM составляет 0.5; `MRS_ARA_TEST_PLUGIN_GAIN` передаёт это значение в generic model suite (по умолчанию 1 для нейтральных внешних fixtures). Оба теста сохраняются.

## Artifacts
Runtime artifact: EXE, VST3-сканер, **ARA2-сканер при обычной сборке**, crash reporter, лицензии, README, source/run provenance, CI-TEST-RESULT.txt и SHA256.json. Символы — отдельным artifact, тестовые logs/JUnit — отдельным. SDK/fixtures/user settings не включаются. При test failure пакет пользовательской приёмки не формируется; логи и символы сохраняются для диагностики, job остаётся FAIL.
Скачать runtime artifact, сверить все SHA256/размеры/Windows version/source, проверить отсутствие SDK/secrets/fixtures/PDB. Затем выполнить user acceptance/hardware проверки. Срок хранения runtime14 дней, symbols7 дней; это Actions Artifact, не автоматический публичный GitHub Release и не подтверждение коммерческой лицензии продукта.

## Риски и приёмка
Не маскировать исторические регрессии (включая #239), не отключать тесты, warnings и обязательные проверки ради зелёного CI. Устранять первую содержательную ошибку и повторять затронутый контур; полный — только когда это требуется для кандидата или области риска.

No alloc/free/locks/I/O/UI в callback; Commands/Undo/project/media сохраняются. CI PASS не подтверждает физическую ASIO latency/xruns, слух, native mixed-DPI или совместимость всех vendors. Результаты, ссылки на запуск/артефакт и ограничения фиксируются в чате и техническом описании PR; #241 — архив миграции. Merge в `main` — только после пользовательской приёмки и согласования. Не создавай и не изменяй Issues для текущих заданий без отдельного поручения.
