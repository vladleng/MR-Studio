# MR Saturator — техническое задание и план реализации

**Статус:** концепция / backlog; **реализация не начата**. **Продукт:** Moon River Studio (MRS).  
**Дата:** 2026-10-09. **Источник:** обсуждение пользователя о нативном сатураторе, качестве DSP и разделении Studio / Live.  
**Связанные документы:** [DSP modeling](DSP_MODELING.md), [Native Inserts](NATIVE_INSERTS.md), [Processing Reliability](PROCESSING_RELIABILITY.md), [Performance plan](ENGINE_PERFORMANCE_PLAN.md), [Development tracks](DEVELOPMENT_TRACKS.md), [Project context](PROJECT_CONTEXT.md).  
**Трекинг:** отдельная parent issue MR Saturator в направлении [NATIVE PLUGINS #111](https://github.com/vladleng/MR-Studio/issues/111); ссылки на задачи — в parent issue. Это **будущая собственная функция**; не означает запуск Stage 3d/3e, смену активного этапа или изменение текущего состояния проекта.

## 1. Задача и продуктовая граница

Создать собственный качественный, расширяемый нативный сатуратор на C++ / JUCE, использующий **общий SHARED processor graph** и имеющиеся insert chains (track, bus, Master). DSP должен быть пригоден для последующего использования в channel strip и, при отдельном решении, в VST3; **не создавать второй движок**.

**Главное решение пользователя:** не переносить ограничения MR Live на все инструменты сведения в MR Studio. Сведение обычно выполняется с увеличенным буфером (например, 512–2048 frames, значения ориентировочные, не принудительные), а низкий буфер вроде 128 frames в Studio нужен прежде всего при записи/мониторинге. При микшировании приоритет — качество алгоритмов; при записи — корректный мониторинг и управляемая задержка. Live Mode — отдельный рабочий сценарий той же DAW, не отдельный продукт или backend.

Обязательные требования к нативному DSP (отсутствие host allocations / файлового I/O / блокировок на аудиопути, безопасное состояние и предсказуемая обработка) сохраняются **во всех режимах**, в том числе при большом буфере.

### Разделение сценариев

| Сценарий | Приоритет | Поведение |
| --- | --- | --- |
| Studio / Mix | Качество, гибкость, сохраняемость и CPU-эффективность на больших сессиях | Допускаются качественные фильтры, oversampling, сложные модели и корректно учтённая latency. |
| Studio / Record / input monitoring | Рабочая задержка и стабильность записи | Предлагать облегчённый профиль, показывать monitoring latency, уважать PDC и существующий mixed renderer; не отключать молча обработки. Raw recording остаётся raw. |
| Studio / Offline export | Качество и детерминированный render | Разрешить более тяжёлый явно выбранный профиль после измерений; корректно учитывать задержку и хвосты. |
| Live Mode (в будущем) | Стабильность и низкая задержка | Отдельная проверка live-safe профилей/метаданных; не требовать от всей модели zero-latency и не обещать, что все модели доступны live. |

Числа oversampling и буфера ниже — **кандидаты на измерение**, а не принятые обязательные режимы или гарантия превосходства.

## 2. Архитектура сигнала

~~~text
Input
  -> Input/Drive gain (smoothed)
  -> Optional pre-emphasis / input conditioning
  -> [Oversampling: upsample -> model-specific nonlinear DSP -> downsample]
  -> Optional post tone / de-emphasis + DC control
  -> Processed wet
  -> Latency-aligned dry/wet crossfade
  -> Output trim / optional measured gain compensation
  -> Output
~~~

- Pre/post tone и компенсация громкости должны иметь чётко определённый порядок относительно Dry/Wet; предусмотреть тест на согласование фаз и задержек.
- Oversampling применяется к участкам, для которых нужен высокий sample rate; фильтры вне oversampled области работают на project sample rate по обоснованному выбору модели.
- Объединяющий DSP API скрывает конкретную реализацию моделей, но **не маскирует** разную задержку, динамическую память и расход CPU.
- Один экземпляр имеет независимые состояния на каждый канал; mono / stereo, корректное отсутствие непреднамеренных cross-channel связей. Возможно поддержать dual-mono / linked mode позднее, если появится задача.
- Не обходить существующие правила graph, PDC, вставки, automation, Undo/Redo и snapshot persistence.

## 3. Модели насыщения

| Model ID (stable) | Начальный подход | Ожидаемый характер | Scope |
| --- | --- | --- | --- |
| **Clean** | Контролируемый симметричный soft clipping / waveshaping с unity/trim | Лёгкое насыщение | MVP |
| **Tube** | Асимметричная нелинейность с корректным bias/DC и gain staging | Пропорции чётных/нечётных гармоник, зависящие от драйва | MVP; дальнейшая физическая модель отдельно |
| **Tape** | Модель с памятью / динамической нелинейностью, частотной зависимостью, фильтрами | Компрессия транзиентов и окраска | Следующий этап, НЕ простая atan-кривая под видом tape |
| **Console** | Очень лёгкая нелинейность / частотная окраска с низкой нагрузкой | Использование на многих каналах | Следующий этап |
| **Drive** | Более агрессивная нелинейность с контролем алиасинга | Выраженная сатурация | Следующий этап |

**Нельзя обозначать простую произвольную transfer curve как достоверную эмуляцию физической ленты или лампового устройства.** Стартовые модели — музыкальные DSP-алгоритмы, а не слепки конкретного оборудования. Имена указывают характер обработки; точность физических эмуляций — отдельная R&D задача.

Технические условия:
- Drive должен влиять на реальный input stage, а не быть только UI-процентом.
- При нулевом Drive — описанное нейтральное/минимальное поведение, без неожиданного скачка уровня и без самопроизвольной окраски, если модель это не декларирует.
- Асимметричные модели: контролируемый DC offset; корректная работа с тишиной, субнизом, отрицательными пиками и denormals.
- Для Tape: явный сброс/инициализация памяти при prepare, seek/transport согласно выбранному контракту; проверка непрерывности state при playback.
- Названия / stable IDs моделей не должны ломать ранее сохранённые проекты при добавлении новых моделей.

## 4. Anti-aliasing / качество

**Основной кандидат — JUCE dsp::Oversampling.** Изучить качество FIR/IIR фильтров, латентность, стоимость и жизненный цикл buffer при 2×/4×/8×; 16× — кандидат прежде всего для offline/export по результатам тестов. Перечень 2×/4×/8×/16× — **не обязательная матрица релиза**. Не зашивать «чем больше, тем лучше» в UI без проверки спектра и нагрузки.

**ADAA (Antiderivative Antialiasing)** исследовать для математически подходящих waveshapers. ADAA **не** гарантирует устранения всего алиасинга, не заменяет автоматически oversampling и не обязательно применим к моделям с памятью. Рассмотреть собственную реализацию с проверенной математикой/тестами либо совместимую по лицензии библиотеку. **Не копировать код третьих сторон до проверки лицензии**, особенно GPL/обязательств при будущем коммерческом распространении.

- Oversampling filter phase/delay и dry/wet alignment измеряются, а не предполагаются.
- Протестировать 44.1 / 48 / 96 / 192 kHz, short and irregular blocks, silence, impulses, swept sine, full-scale и экстремальные значения параметров.
- Оценить уровень алиасинга и спектр гармоник на разных основных частотах / sample rates.
- Сравнить plain waveshaping, ADAA (где применимо), oversampling и их комбинацию по качеству и CPU.
- Выбор default quality делать **после** сравнения измерений и слухового теста, а не по одной визуальной кривой.

## 5. Параметры, автоматика, UX

Обязательные управляемые параметры:
- **Model**: Clean / Tube / Tape / Console / Drive (по мере реализации, без пустых обещающих пунктов).
- **Drive**: интерпретируемая характеристика насыщения (процент или dB; до реализации выбрать контракт и диапазон).
- **Tone**: простая понятная коррекция, единый диапазон либо model-specific функция (решить и задокументировать).
- **Mix**: 0–100%, *latency-aligned* dry/wet; сохранить адекватную амплитуду/фазу на 50%.
- **Output**: выходная коррекция в dB с управляемыми границами и smoothing.
- **Quality**: доступные проверенные профили, при изменении требующие неблокирующего reprepare/safe swap.
- **Bypass**: корректные latency/PDC и click-free переключения, тест Undo и state restore.
- **Optional Auto Gain**: только при внятной модели целевого уровня и тестах; не маскировать ложно качество A/B.

UI: компактный графитово-серый стиль в существующей теме JUCE, окно native insert; сначала корректная работа и доступность, затем иллюстративная transfer curve / спектр (визуализация **не является DSP**). Управление с клавиатуры/мыши, читаемые значения, масштабирование DPI, без кракозябр. Реальный график должен совпадать с измеренной статической характеристикой выбранной модели либо быть явно помечен иллюстрацией (для динамической Tape не выдавать статическую кривую за полное поведение).

Все изменения проходят через существующие команды/parameter flow и Undo/Redo. Persist: model ID, Drive, Tone, Mix, Output, Quality, bypass, будущие независимые параметры; presets с миграцией/совместимостью схемы. Параметры сглаживаются; тестируются быстрые automation sweeps, очереди updates, проект save/reopen и sample-rate changes.

## 6. Realtime safety, PDC и режимы качества

- Prepare/allocate в не-RT; никаких новых host allocations, locks, file I/O, UI, сети в audio callback; bounded state, denormal/NaN/Inf protections.
- Без изменения существующего pipeline raw record; insert работает на маршруте monitoring/playback согласно правилам DAW.
- Sample-accurate или block-accurate automation — выбрать согласно реальному параметрическому контракту хоста; не заявлять sample-accurate без реализации.
- Quality/model switch, меняющий latency или подготовленные буферы, выполняется через подготовленное состояние и safe transition; не уничтожать активный объект из callback.
- Указать алгоритмическую латентность и integration с действующей PDC. Dry/Wet всегда согласован; bypass и смена профиля не дают скачка времени. Принять реальные ограничения текущей PDC, не объявлять её полностью завершённой.
- Для monitoring: классифицировать конкретную модель/профиль по измеренной latency/CPU, **не отключать молча** высоколатентную обработку; если реальный path не поддерживает модель, показать предупреждение/ограничение.
- Сведение при высоком буфере допускает более тяжёлую обработку, но рост числа экземпляров не должен быть неоправданным. Измерять 1/8/32+ экземпляров в реалистичном graph и на ожидаемом оборудовании.
- Live Mode не входит в MVP. Позднее возможно добавить отдельно подтверждённую live-safe конфигурацию без fork DSP engine.

## 7. Предлагаемые фазы реализации (отдельные issues)

1. **DSP foundation + Clean / Tube MVP:** API, процессор, каналы, gain stages, smoothing, DC/denormal, интеграционный скелет, тестовые эталоны.
2. **Anti-aliasing / Oversampling + PDC:** измерения JUCE oversampling, ADAA spike/prototype, quality switching, dry/wet delay, мониторинг/report latency.
3. **Character models:** Tape / Console / Drive как осмысленные отдельные модели с тестируемым откликом; не обещать физическую достоверность.
4. **Native UI + persistence + automation:** интеграция в вставки, управление, сохранение, Undo, график, пресеты / quality profiles.
5. **QA + profiling + acceptance:** аудиоизмерения, CPU, latency, reliability, regression, локальный пакет и пользовательская приёмка.

Порядок допускает небольшие технические пересечения между фазами. Каждая issue должна указывать зависимости, out-of-scope и проверяемые acceptance criteria. **Ни один этап не отмечать выполненным без соответствующей локальной реализации и проверки.**

## 8. Приёмка / тестовые сценарии

### Обязательные автоматические
- Непрерывные и конечные выходы при тишине, impulsive, noise, loud/low-level input, всех граничных параметрах, множественных sample rates и block sizes.
- Mono/stereo independence и отсутствие разрыва состояния при вариациях buffer.
- Измеренный гармонический спектр (THD/частотозависимый отклик), алиасинг и DC component; выходной уровень и контроль overs при сравнимой громкости.
- Сопоставление 1×/2×/4×/8× при справедливой калибровке latency; 16× по необходимости.
- Dry/Wet null/impulse alignment и PDC между параллельными маршрутами, при bypass и quality change.
- Automation continuity / parameter smoothing; NaN/Inf/denormal; no host allocation in callback; lock-free processing contract.
- Undo/Redo, preset save/restore, project re-open, legacy snapshots, ASIO restart/sample-rate changes; запись остаётся raw.
- Численные и нагрузочные тесты на цепях с другими эффектами и на множестве дорожек. Не интерпретировать один offline benchmark как гарантию real-ASIO производительности.

### Ручная приёмка
- Слуховая проверка Clean/Tube/Tape/Console/Drive при **согласованной громкости**, включая drums, bass, guitar, piano, vocals и master bus по доступности тестовых материалов.
- Проверка отсутствия щелчков при плавных изменениях и переключении режимов.
- Отдельные проверки: mix в обычном студийном буфере; Studio record/monitor с низким буфером; offline render.
- Проверка GUI в целевой теме/DPI, сохранения проектов/пресетов и совместимости существующего processing graph.

## 9. Не входит в первый scope

Отдельный VST3 build / продажа / копирование аппаратных моделей, neural capture training, полноценный channel strip для каждой дорожки, отдельный backend для Live, гарантированное 16× realtime, физически точная tape/tube эмуляция, расширенные Mid/Side или multiband processing. Это будущие отдельные решения на основе опыта с MVP.
