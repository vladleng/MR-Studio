# Локальная разработка, сборки и приёмка

**Действующий процесс — решение пользователя от 2026-11-16.** Разработка MR Studio / MR Live, сборки, тесты и подготовка пакетов выполняются на локальном Windows-ПК. GitHub используется только для Issues и обсуждения задач. Эта политика заменяет онлайн-процесс от 2026-11-08; [облачная схема](CLOUD_DEVELOPMENT.md) сохранена для истории. Общие правила — [AGENTS.md](../AGENTS.md), выбор проверок — [Build/Test Skill](../.agents/skills/mr-studio-build-test/SKILL.md).

## Хранение и воспроизводимость

- Checkout и локальная история Git — источник кода, правил и спецификаций. В Git сохраняются исходники, тесты, ресурсы, scripts/configs и skills; работа ведётся в тематических ветках с сохранением незакоммиченных изменений. Исходники и Git необходимо резервировать отдельно от ПК; Issues не заменяют резервную копию.
- Visual Studio с MSVC, Windows SDK, CMake и другие инструменты устанавливаются в Windows вне checkout. SDK зависимостей получают по закреплённым версиям `tools/ci/sdk-lock.json`, проверяя commits и ASIO checksum; подготовка SDK является отдельным этапом, а не следствием правки документации.
- SDK, кэши, сборки, символы и тестовые логи размещаются в исключённых из Git локальных каталогах. Подготовка и локальный скрипт сборки используют `build/sdk` и `build/private-sdk`. Наличие каталога или скрипта не доказывает готовность среды.
- Готовый runtime для приёмки размещается в отдельной папке вне checkout. Запуск из `build/` может нарушать сохранение проектов и диагностики из-за ограничений записи. Предыдущие принятые сборки, проекты, настройки, SDK и пользовательские WAV/NAM сохраняются.

## Вход в Developer PowerShell

Из PowerShell в корне checkout выполни `& .\tools\Enter-DevEnvironment.ps1`. Скрипт находит завершённую установку Visual Studio 18 с MSVC, включает окружение host/target x64, проверяет Windows SDK и добавляет CMake/Ninja в PATH текущего процесса. При необходимости выбери установку через `-VsInstallationPath '<каталог Visual Studio>'`. Текущий каталог, пользовательский профиль и системный PATH не меняются; повтори вход в каждом новом PowerShell-сеансе. Скрипт не устанавливает зависимости, не скачивает SDK и не запускает сборки.

DSH запускается обычным способом. Для команд сборки предварительный вход не нужен: `Build-Local.ps1` подключает окружение самостоятельно. Профили, настройки и skills DSH при этом не изменяются.

## Команды локальной сборки

[`tools/Build-Local.ps1`](../tools/Build-Local.ps1) сам подключает окружение, работает с подготовленными SDK и ничего не скачивает. Профили `-Product Core|Studio|Live|Both` используют отдельные деревья `build/local-windows/<profile>`; по умолчанию выбран **Studio**, ARA ON, Live OFF. Профиль Live использует ARA OFF. `-NoAra` создаёт отдельное диагностическое дерево Studio/Both. `-BuildDir` задаёт другое дерево явно; относительные пути разрешаются от корня checkout.

```powershell
# Просмотр плана без configure, компиляции и тестов:
& .\tools\Build-Local.ps1 -Product Studio -DryRun | ConvertTo-Json -Depth 6
# Адресная сборка и тест Core:
& .\tools\Build-Local.ps1 -Product Core -Target mrs_core_tests -Jobs 1
& .\tools\Build-Local.ps1 -Step Test -Product Core -TestRegex '^core_(model|timeline|transport|commands|serialization)$'
# Отдельные приложения:
& .\tools\Build-Local.ps1 -Product Studio -Jobs 1
& .\tools\Build-Local.ps1 -Product Live -Jobs 1
```

`-Step Configure|Build|Test|All` выбирает действие. Build выполняет configure и собирает только указанные `-Target` либо приложение выбранного профиля; Core по умолчанию собирает `mrs_core_tests`. Both собирает Studio с её существующей зависимостью от Live. `-Jobs` ограничивает параллелизм, `-Configuration` выбирает Release/Debug/RelWithDebInfo. Скрипт не упаковывает runtime и не меняет ярлыки приложений.

Test не запускает configure или build, проверяет соответствие дерева выбранным параметрам и требует `-TestRegex` либо явно выбранный `-Full`. Для тестовых fixtures TEMP/TMP временно направляются в `<build-dir>/Testing/Temp` и восстанавливаются после прогона, в том числе при ошибке. All выполняет configure, адресную сборку и выбранные тесты. Нужные тестовые targets необходимо собрать явно; `-Full` само по себе не собирает все тесты и допускается лишь по правилам L4.

Для ARA render/model-проверок добавь `-AraFixture` при configure/build/test. Fixture конфигурируется отдельно; при Build/All она собирается до конфигурации продукта. Обеим suite передаётся один и тот же plugin с ожидаемым gain 0.5. Configure только подготавливает деревья, поэтому перед тестами нужна сборка fixture. Полный прогон профиля с ARA требует `-AraFixture`; Live/Core этот параметр отклоняют. Статические проверки интерфейса скрипта: `& .\tools\tests\Local-Workflow.Tests.ps1`.

## Работа и проверки

1. Начинай с конкретного запроса или назначенной Issue, проверяй локальные status, branch и HEAD. Читай только затронутые контракты и код. Не заменяй локальную ветку опубликованным состоянием GitHub.
2. Перед сборкой читай фактические `tools/Build-Local.ps1`, CMake и presets; не используй несуществующие параметры. Скрипт подготовки `tools/ci/Prepare-Sdks.ps1` можно использовать локально, но его пути должны совпадать с конфигурацией сборки. Документация не подменяет проверку действующего интерфейса.
3. Выбирай адресные targets и тесты по риску, начиная с Core/контрактов. Для багфиксов обязателен RED → GREEN. Docs-only не требует сборок; косметические изменения сохраняют исключения из AGENTS. Полный CTest — для согласованного кандидата либо при конкретном техническом основании.
4. Studio по умолчанию с ARA2; Live standalone всегда без ARA2. При совместной сборке ARA2 ограничена Studio. Studio ARA-OFF — только по явному диагностическому запросу. Studio-only задача не запускает Live автоматически.
5. Фиксируй точную ревизию, dirty state, конфигурацию, команды и PASS/FAIL/NOT TESTED. Локальные логи остаются вне Git; содержательные результаты и приёмка записываются в назначенную Issue. Успешная сборка не доказывает фактическую ASIO/MIDI/DPI/vendor проверку и не заменяет пользовательскую приёмку.

## GitHub и границы полномочий

Push кода или правил, создание PR, запуск Actions и публикация пакетов не входят в стандартный процесс и требуют отдельного запроса пользователя. Существующие workflows сохраняются как историческая конфигурация; их изменение/удаление не является частью перехода правил. Если удалённая работа отдельно запрошена, действуют фактические gates и permissions, без обхода проверок.

Merge в локальный `main` требует отдельного явного разрешения. Issue/Sub-issue закрывается как Completed после явной пользовательской приёмки соответствующего объёма. SDK, секреты, защищённые сторонние материалы и пользовательские файлы не публикуются.
