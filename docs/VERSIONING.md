# MR Studio / MR Live — версионирование

Каноническая схема версий для локальных сборок. Читать при назначении версии или подготовке пакета; общие полномочия определяет [AGENTS.md](../AGENTS.md).

Единая схема для соответствующей линии разработки: **`0.I.S`** (например, `0.8.8`).

- **Первая цифра** (`0`) — основной этап разработки; меняется только по отдельному согласованному решению.
- **Вторая цифра** (`I`) — номер этапа родительской задачи DSH; увеличивается **только при старте следующей родительской задачи DSH**, не при исправлениях, коммитах, PR или сборках. Пример: `0.8.0 → 0.9.0`.
- **Третья цифра** (`S`) — порядковый номер подзадачи в текущей родительской задаче DSH: `0.8.1`, `0.8.2`, …; при переходе к новой родительской задаче DSH сбрасывается в `0`. Если подзадач нет, используется версия `0.8.0`.
- **Исправление ошибки** текущей версии — суффикс `-fix1`, `-fix2`, … (например, `0.8.8-fix1`). Ошибки и регрессии не увеличивают базовую версию.
- **Небольшое дополнение** в рамках той же подзадачи DSH — суффикс `-Upd1`, `-Upd2`, … (например, `0.8.8-Upd1`). Значительные дополнения оформляй отдельной подзадачей DSH.
- Счётчики `fix` и `Upd` **независимы** в пределах базовой версии. Новая подзадача DSH начинается без суффиксов; число коммитов, PR и Actions runs на версию не влияет.
- **Версирование касается готовых билдов:** после падения локальной сборки или тестов исправляй причину и повторяй проверку в рамках текущей версии, без увеличения `fix`/`Upd` из-за неудачного запуска. Следующий номер назначай следующему готовому билду; ранее выпущенные билды задним числом не переименовывай.
- Для отдельных компонентов экосистемы допускаются **независимые последовательности версий**: новая задача DSH MR Live сама по себе не повышает версию MR Studio DAW.
- **Одна версия на весь запуск сборки:** версия приложения, package manifest, имена каталога/ZIP и всех создаваемых пакетов, символов и диагностических результатов должны содержать одну точную версию соответствующего компонента, включая `-fixN`/`-UpdN`. SHA дополняет идентификацию, но не заменяет версию.
- **Синхронизация версии:** используй единый источник версии для приложения, package manifest и имён пакетов. В совместной сборке Studio/Live указывай версии каждого компонента явно. Несоответствия исправляй до выдачи нового пакета, без переименования ранее принятых версий.
- **Версия Studio:** значение из `apps/studio-desktop/include/mrs/version.hpp` должно совпадать в баннере приложения, manifest и именах каталога/ZIP пакета. Версия Live определяется её собственным источником.
- Идентификатор задачи DSH **не равен** номеру версии. Указывай версию этапа в задаче и отчёте, не переименовывай принятые версии задним числом без согласования. Перенос задач из GitHub и порядок отображения в DSH не меняют версии, номера этапов и порядковые номера подзадач; прежние номера GitHub Issues сохраняются только для истории.
- Успешная сборка не означает пользовательскую приёмку версии. Не переводи задачу DSH в `done` и не делай merge только из-за PASS проверок.

Статус, принятые версии и историю решений фиксировать в соответствующей задаче DSH Task Manager, проект «MR Studio»; не вести здесь таблицу текущих сборок. Исторические правила доступны в Git.
